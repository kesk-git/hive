# Hive design

Design baseline: 2026-10-10. This is an implementation contract, not a claim that the components below already exist.

Product scope follows the Hive Mind's 2026-10-10 brainstorm rulings and later Codex findings and decisions, including the decision to park Codex Cloud work without model selection, and the 2026-10-11 ruling that Synapse is local-first: its checks and both its reviewers run on the Mac, GitHub is one optional publisher of its results and never the gate, and where a Hunt runs, on the Mac or in the Void, is a choice made for that Hunt; and the ruling later that day on the shape of the gate's stage: Synapse runs over no-mistakes on the Mac as a long-lived plugin point, which makes six dependencies, and the native local gate is deferred until after the pilot, in which Hive supervises its own stages 6 and 7. The dated Claude and Codex measurements establish the capability evidence; the original firstmate supplies the inherited operational contracts.

Hive specializes firstmate for Claude Code and Codex. It retains their local execution and supervision contracts, owns the workflow natively, and adds execution in the Void. The Hive and its Fleets ordinarily run as Claude Code sessions on the Mac; local Codex supervision remains an inherited capability. Swarms and Lictors run on the Mac or in the Void, and which it is for a Hunt is a choice made for that Hunt: on the Mac, in a Claude cloud session, and later, once its route is qualified, in Codex Cloud. A Prey that needs one worker is a single Hunt, so a choice made for a Hunt is made for it. Hive is the proof of concept of that hybrid, and the difference from the inherited workflow, which runs everything locally, is exactly where a Hunt may run. A Hunt lands through its own validation, as its Imperative's delivery records it: where the Imperative selects Synapse validation, Synapse validates the result on the Mac, whichever place built it, in a run of that Hunt's own; a direct Harvest goes to publication and its stated checks with no Synapse run; and Assimilation stays on the Mac. Hive keeps no secret of its own; the one statement of that contract is [Secrets: Hive keeps none](#secrets-hive-keeps-none), and every other section refers to it.

The approved tooling ruling, as amended on 2026-10-11, narrows the inherited implementation to one repository and six core dependencies: Git, gh, tmux, Claude Code, Codex CLI and no-mistakes, the last as the long-lived plugin point behind Synapse. Local Swarms, owned worktrees and supervision remain; Hive builds its own workflow, the Synapse contract over that plugin and its review surface, and a native local gate is a later stage after the pilot. Project-specific test environments stay with their projects. The plugin point and the optional browser exception are defined in [Tooling](#tooling). This design does not alter the existing firstmate installation.

Claude is the primary Void executor, through Claude Code cloud sessions and the official GitHub integration. Codex remains a second executor behind the same Hive interface, with three interchangeable backends: local on the Mac, legacy Void, and new Void. Both Codex Cloud backends are parked; local Codex is the active route. Re-enabling Void work requires a supported command-line path that honors model selection and meets the collection contract. Interchangeability preserves the task contract; it does not imply equal capabilities or permission to change a task's model or placement silently.

The later Mind's word parks Codex Cloud work because the legacy path cannot choose the model. Its successful submission, status, diff and apply measurement and internal final-text retrieval remain useful evidence; they do not authorize dispatch without model control. Astra reviews stay on local Codex on the Mac. Codex usage, including compatibility probes, is command line only: no browser-driven tasks or GitHub mention or Action dispatch. Legacy retirement must leave Claude delivery and local Codex operational.

## Vocabulary and placement

| Name | Meaning and responsibility |
| --- | --- |
| Hive | The product. **The Hive** is its primary supervisor and the Hive Mind's point of contact. |
| Hive Mind | The operator; supplies intent, scope, decisions, and Assimilation authority. |
| Fleet | A persistent workspace supervisor, named after its workspace, with one isolated private home, one Pool and a charter registering the projects it supervises. |
| Expanse | The Hive-wide view across every workspace: a projection, not another supervisor or queue. |
| Sector | A workspace as the UI names it: one Fleet with its private home and Pool, and the projects registered under it. |
| Subsector | A project as the UI names it: one registration under a Sector, keeping its own repository and clone, validation, publication and authority references. |
| Swarm | A worker completing an authorized change through its chosen delivery path. |
| Lictor | An investigator producing evidence, a diagnosis, or a design report; research alone does not authorize implementation. |
| Imperative | The complete dispatch instructions for one assignment. |
| Pool | The durable work queue owned by the Hive or a Fleet. |
| Wave | The fourth level of the work hierarchy: an ordered group of Targets with an outcome on a project's roadmap. It is recorded as grouping data on each of its Targets, its slug, title and ordinal, and has no worker, no Pool item of its own, no owner and no state of its own. |
| Target | One outcome on a project's roadmap, in the Hive Mind's words, with the Targets it depends on and any act of the Hive Mind beside it. A Target has no hunter, no Imperative, no generation and no place. It consists of Prey, which its define step draws, and it is complete when every one of its Prey has landed, and by nothing else. |
| Prey | One deliverable of a Target, drawn by the define step with a title and an explanation, deliverable on its own and taken beside its siblings where possible. It is taken by one or more Hunts: a Prey that needs one hunter is a single Hunt, and one that needs several holds Hunts named a, b, c under it and lands when every Hunt has landed. A follow-up, a residue fix, a relaunch or a Lictor dispatched from its filed record is a Prey that belongs to no Target. |
| Hunt | One hunter's engagement with one Prey in one place, named a, b, c under the Prey, sized to one build group and, where its validation is Synapse, one Synapse run, and returning a Harvest where one is selected. A Hunt is one Pool item with one Imperative, one place and one generation at a time. It is the only level of the hierarchy that has a worker. |
| Spawning Pool | The Hive-owned set of isolated worktrees and their leases, from which a local Swarm or Lictor is given its working copy. It holds working copies, never the Pool's items: it is neither the Pool nor a part of it, and its name is always written in full. |
| Mind's word | An operator decision, recorded against a held Pool item. |
| Shadow | Supervision, durable observation and wake ownership. |
| Synapse | The review and validation gate. It runs on the Mac for every delivery that selects validation, whichever place built the head, over no-mistakes as a long-lived plugin point; GitHub is at most a publisher of its results. |
| Harvest | A pull request carrying a proposed change. |
| Assimilation | Authorized merging of a Harvest or landing of a local-only change. |
| Void | Cloud execution: a place a Hunt may run, chosen for that Hunt. Model names remain their real names. |
| Genestealer | The research role developing Hive; it does not create another level of runtime authority. |
| Spoor | The durable reference to one secret, never the value; defined under [Secrets](#secrets-hive-keeps-none). |
| Tendril | The one small audited launcher that resolves a Spoor into the one command that needs it; defined under [Secrets](#secrets-hive-keeps-none). |

Expanse, Sector and Subsector name scope in the UI. They add no runtime authority level, and labels use them alone, without a Workspace or Project prefix. Workspace, Fleet home, project and clone are separate identities even when a deployment starts with one of each.

The work hierarchy is the Hive, a Fleet, a project, then a Wave, a Target, a Prey and a Hunt, with Hunts under a Prey where it needs them. A Fleet occupies a Sector and sends its hunters into its Subsectors; the Swarm is the agents, and Waves, Targets, Prey and Hunts are what the Swarm acts on, never part of it. A Fleet supervises the projects of its workspace; a project's roadmap holds its Targets in Waves, and a Wave groups Targets, in order, under one outcome; a Target consists of Prey; a worker takes a Hunt, or a Prey that is a single Hunt. A Hunt is the only level with a worker. The state of a Target, and of a Prey that holds Hunts, is read off the landings beneath it and from nothing else. Every record, view and label uses these names in this order, and a record or view that has no place for one of them is a defect. Each level has its record:

| Level | Record | Shown as |
| --- | --- | --- |
| The Hive | The home record with the Hive's role | The Expanse and the session dock |
| Fleet | The home record with a Fleet's role, and its workspace record | A Sector and its flagship |
| Project | The project record registered under its Fleet's charter | A Subsector |
| Wave | No record of its own: its slug, title and ordinal are grouping data on the Pool item of each of its Targets | The roadmap, which orders its Targets by their Wave; Waves are also the Pool's group headers in roadmap order, and never appear on the map |
| Target | A Pool item of level target in the Pool of the Fleet that owns the project, or in the Hive's Pool for the Hive's own stages; it carries its Wave, the fourth level, as grouping data, the Wave's slug, title and ordinal | The Pool and the task inspector, with its Prey beneath it |
| Prey | A Pool item of level prey, with a parent edge to its Target, or no parent edge when it belongs to no Target | The Pool and the task inspector, with its Hunts beneath it where it holds them |
| Hunt | A Pool item of level hunt, with a parent edge to its Prey; the only item with an Imperative, a place and a generation | The Pool, the task inspector and a task planet with its worker |

Hive uses its own visual identity. Do not use Tyranid, Warhammer or Games Workshop artwork in its interface, documentation or promotional material.

GitHub delivers events to its Actions and vendor integrations. It does not deliver webhooks into the Mac supervisor session. The Shadow therefore polls and wakes the appropriate supervisor. No always-running supervisor or waiting loop is placed in a Void session.

## What Hive keeps from firstmate

The inheritance baseline is the original [firstmate operator contract](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/AGENTS.md), [architecture](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/docs/architecture.md), and [configuration](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/docs/configuration.md). This snapshot makes the comparison reproducible; implementation must review later upstream changes before porting them.

### Operator contract and hard rules

1. The Hive coordinates work; Swarms change projects. Fleets apply the same separation within their charters. Guarded initialization, synchronization, updates, and authorized Assimilation keep their narrow upstream exceptions. A concrete instruction from the Hive Mind can authorize a specific project operation, but cannot be broadened into standing authority.
2. Assimilation requires the Hive Mind's explicit word, or an explicitly granted project posture permitting autonomous Assimilation of green, in-scope work. A worker, reviewer, passing check, or completed Void session cannot grant that authority.
3. Preserve unlanded work. A dirty worktree, uncertain ownership, an uncollected result, or an unproved remote copy blocks cleanup. A Lictor's scratch copy can be retired only after its report is safely collected and its decision inventory recorded.
4. Swarms and Lictors report to their dispatching supervisor. Fleets relay outcomes through their registered parent channel. Direct intervention by the Hive Mind remains authoritative and is reconciled into the durable record.
5. Report outcomes faithfully: distinguish an accepted launch, observed activity, published change, passing Synapse, and completed Assimilation. Missing evidence is unknown, not success. A claim names what was examined, and what was not examined is reported as not examined, never as unaffected.

The Hive presents concrete outcomes and the decisions needed from the Hive Mind, including a Harvest's full URL when relevant. An idle Fleet does not invent audits or improvement work. Research is dispatched separately only when requested or when uncertainty could change whether or what to build; bounded research can remain within an already authorized implementation task.

### Retained capabilities

| Capability | Hive contract |
| --- | --- |
| Local Claude and Codex | Preserve verified launch, steering, interruption, exit, resume, recovery, model/effort configuration, permission modes, and tool restrictions. Harness choice and runtime placement are separate axes. |
| Isolated worktrees and terminal runtime | Preserve disposable copies, durable ownership and visible sessions through the Spawning Pool and tmux. Runtime interfaces remain extensible, but additional terminal installations are not part of the selected profile. |
| Synapse continuity | Synapse runs over no-mistakes on the Mac as a long-lived plugin point. A native local gate is a later stage after the pilot and replaces the plugin for a route only when it proves that route's validation and custody contracts. A worker drives the selected executor's gates and does not edit around an active run. |
| Delivery choices | Model placement, validation, publication and Assimilation authority independently. Preserve the upstream `no-mistakes`, `direct-PR` and `local-only` inputs through explicit translation; local-only publication never disables validation by implication. |
| Project-specific proof | Each project supplies its test commands, execution environments and capacity management. Hive collects revision-bound results without owning that infrastructure. macOS behavior still requires native macOS proof; a Linux Void session cannot establish it. |
| Persistent Fleets | Preserve charters, isolated homes, scope routing, correlated parent replies, guarded provisioning and recovery. Existing remote-home capability remains optional; the chosen deployment starts with supervisors on the Mac. |
| Supervision and continuity | Preserve durable inboxes, status events, wake acknowledgments, current-state reconciliation, turn-end guards, away/quiet operation, stow, and guarded restart/update behavior for Claude and Codex. |
| Project and operational tooling | Keep project registration, branch/base selection, GitHub binding, native Pool, usage-aware admission and guarded synchronization for Claude/Codex work. Preserve validated local-only delivery without introducing unselected forge, communication or queue dependencies. |

Local-only work stays under the Hive's local landing authority. A direct Harvest does not acquire an additional independent review pipeline merely because it uses Claude or Codex. The Synapse contract below is the one validated delivery path, on the Mac, for work built on the Mac and work built in the Void alike. The Imperative must separately declare validation and publication; a local-only branch still receives its required Synapse checks. A repository's own required checks remain that repository's merge precondition, read at Assimilation; they are not the gate.

### Native workflow, configurable policy and executors

Hive owns admission, definitions, task and decision identity, effective policy, evidence linkage, lifecycle transitions and knowledge projections through the packages in [Tooling](#tooling).
Historical records remain evidence and do not automatically become effective instructions.
The existing firstmate operation stays untouched.

| Boundary | Responsibility |
| --- | --- |
| Native mechanisms | Validate typed records; enforce authority, scope, revision and ownership; make transitions durable and replayable; render one validated Imperative schema; expose missing evidence and pending propagation. |
| Rules and configuration | Model/class/effort, weighted resource comparison, floors/operators, credit authority, Hunt limits/expiry, review escalation, proof scope, memory/context budgets, compaction, delivery posture and workspace ownership. Values and trials carry scope, provenance and expiry. |
| Native presentation | The `ui` package projects scoped Hive records into the Fleet overview, Pool, The Swarm and the on-demand detail, [Scheduled](#scheduled), artifact and decision surfaces, beside the live Hive session. Every decision answer goes through the `word` package's single intake; bounded session input and policy requests go to the `dispatch` interfaces that own them. Display state cannot authorize an action. |
| External execution | Git, gh, tmux, Claude Code, Codex CLI and no-mistakes are the six core executors. Project-owned checks, run from the Mac in the environment the project supplies, supply execution evidence; no-mistakes is the long-lived plugin point behind Synapse, and the browser stack is selected only for browser tasks. |

An adapter registers its version, scoped capabilities, owner and authentication reference privately and implements only supported operations; the reference is a Spoor under [Secrets](#secrets-hive-keeps-none), never a value.
Requests and receipts bind the owning home and workspace, the project and clone where applicable, task, generation and source revision; the Hive's own projectless operations declare that scope explicitly.
Unsupported operations refuse; an unavailable executor cannot turn a pending obligation into success.

| Executor boundary | Operations and durable receipt | Boundary on failure |
| --- | --- | --- |
| no-mistakes, the Synapse plugin point | Start, observe and respond through its supported CLI; collect run/head evidence and follow branch custody and synchronization. | The active run owns fixes; missing evidence or unknown custody blocks publication/landing. |
| GitHub through gh | Push a branch, publish a Harvest and, where Synapse validation was selected, the gate's attestation, read the repository's own rules and current heads, submit an authorized expected-head merge and verify the result. | Unreadable rules or a changed head blocks publication/Assimilation, as does an unpublished attestation where the project requires it. The forge supplies no merge authority and no verdict: where Synapse validated, the gate's result is the Mac's receipt. |
| Optional browser proof | Use the selected browser stack for navigation, capture and attachments bound to the task and selected page. | Incomplete capture, wrong page or a lost session leaves proof pending; browser access does not enable Codex Cloud dispatch. |
| Project validation | Run the project's declared checks in its supplied environment and collect revision-bound results and artifacts. | Missing environment or required evidence blocks validation; Hive does not provision or administer project infrastructure implicitly. |

Each native projection declares the source/rule/specification revisions it consumes.
Source changes mark dependent projections stale until refresh and acknowledgment; configured drift checks compare those bindings.
A recorded requirement for a check does not prove that an installation already runs it.

## Tooling

The Hive Mind approved the following five-point tooling strategy on 2026-10-10, superseding the scout's earlier dependency proposal, and amended its second point on 2026-10-11: Synapse runs over no-mistakes on the Mac as a long-lived plugin point, which makes six dependencies, and the native local gate is deferred until after the pilot.
This is the implementation contract; this documentation change imports no source and adds no licence file, installations, upgrades or services.

1. **One repository:** keep Hive in `kesk-git/hive`, with internal `pool`, `spawning-pool`, `dispatch`, `shadow`, `synapse`, `word` and `ui` packages behind stable command-line contracts, each with its own tests and test target.
2. **Six core dependencies:** Git, gh, tmux, Claude Code, Codex CLI and no-mistakes. Adapt tasks-axi and Treehouse into Hive; rebuild quota reading, launch/restart, the rule-and-specification store and review presentation natively. no-mistakes is the long-lived plugin point behind Synapse, and a native local gate is deferred until after the pilot; chrome-devtools-axi is optional for browser tasks only. gh-axi is not adopted.
3. **Native workflow and review:** drop OpenSpec and Lavish. Keep verbatim rulings with one rendered rule line, and per-change acceptance criteria in the Imperative and Pool item. Decision cards live in Hive's observability UI and submit through its one decision intake. Project-specific execution environments and test suites belong to each project; unrelated products supply inspiration, not integration contracts.
4. **MIT:** license Hive before any code is taken in, preserve upstream copyright/licence notices, and record every source import and upstream revision.
5. **Order:** licence and contracts, Pool, Spawning Pool, session and metering, gate, review surface within the UI, then end-to-end proof; the native local gate comes after the pilot.

The strategy ruling does not perform its implementation or Assimilate this documentation Harvest.
The licence file was added as its own change before any source import, which it must still precede.
Implementation uses new Hive-owned state and leaves the existing firstmate installation, private homes, worktree pools, status displays and shared no-mistakes configuration untouched.

### Repository and package contracts

The packages are internal ownership and testing boundaries in one repository, not separate services or repositories to create now.
Each exposes versioned requests, structured complete responses, explicit exit/error states and capability declarations through a stable command-line contract.
Cross-package operations carry the home, workspace, applicable project and clone, task, generation, source revision, authority and replay identity required by the operation; private records are never ambient global inputs.
A request or response too large for the platform's per-argument limit travels by file path or standard input, never as one command-line argument, and a record that cannot cross the selected channel whole fails with a named size error and a nonzero exit, never as empty or truncated output that a caller could read as a complete result. Prove, in the integration targets, a record above that limit crossing every cross-package call: it arrives complete, or the caller receives the size error and no partial result. Source: [kunchenguid/firstmate#6830](https://github.com/kunchenguid/firstmate/pull/6830).
The existing `hive-*` interfaces below map into these packages rather than creating a package for every command.

| Package | Owns and exposes | Required package test target |

These are required future per-package targets, not commands already present in this documentation-only repository.
Each target runs that package's owned tests independently; integration targets separately exercise the command-line contracts between packages.
No package may bypass another package's writer by opening its private store directly.
In particular, `ui` reads scoped projections, sends decision answers to `word`, and submits bounded session input and policy requests to the `dispatch` interfaces that own them; `word` uses `pool` for persistence, and neither UI state nor a cached display grants authority.
Packages may be extracted later behind the same contracts; an extracted package is not merged back into the monorepo.
Build tooling and libraries must be declared per package, and the delivered core must not require a separately installed Node, Python or Go toolchain as a seventh runtime prerequisite.
A platform utility a package runs as a separate process is declared in that package's `platform` list with its reason; the first is macOS's own `security`, run only by the launch primitive of [Secrets](#secrets-hive-keeps-none), and that section says why a platform utility is not a seventh dependency.
No new always-on control service is required beyond the Shadow's bounded observation and the UI when selected.

The scout's platform inventory records where capabilities came from; it is not a bootstrap manifest.

### `ui`

Hive is specialized to work with this UI. Its main purpose is to keep the Hive Mind in the Fleet overview most of the time, with convenient use of the live Hive session; it stays small rather than growing a tab for every record. The UI presents Hive's records and never stands in for them: each view reads scoped projections, each mutation goes to the interface that owns it, and nothing drawn on screen is evidence that an action happened.

#### The map and its decoration

The Expanse map keeps its decoration, and the decoration is to be expanded rather than trimmed: a space background, a flagship for each Fleet, task planets, trails and ambient hunter motion, all within Hive's [own visual identity](#vocabulary-and-placement). Flagships share one bounded footprint that holds at every zoom level; the starting values are 96 × 40 CSS pixels on the map, counter-scaled against zoom, with inspector artwork capped at 144 pixels. Size never encodes a number of workers or an amount of allowance, and hunters are illustrative, never an exact count of workers. The camera moves only when the Hive Mind moves it. Appearance settings sit in a disclosure. Sample-event playback and simulated clocks are demonstration aids, kept out of the working flow.

Decoration and operation are separate layers. Ambient motion says nothing about work; only the effects in the animation contract are tied to records.

#### Animation contract

The actions the Hive Mind takes through the terminal animate on the map. Every operational effect is permitted by a recorded receipt or a fresh supported observation, never by typed text, optimistic state or display continuity. An instruction typed in the dock and one typed in an external terminal produce the same records and therefore the same effects.

**Timing, replay and freshness.** Receipts written locally (an instruction accepted or routed, a decision answer accepted, a policy request, a stow request) reach the projection as soon as they are durable, so the map answers promptly. Remote activity waits for a supported observation on the Shadow's [bounded cadence](#the-shadow); an unsupported status stays visibly unknown. Each effect consumes a stable event ID and task generation, keeps occurred, observed and received times apart, and is deduplicated by source, event and generation, so neither a reconnect nor a reused vendor handle fires it twice. Initial load and recovery establish current state from a snapshot and do not replay the backlog as fresh activity. A burst coalesces within a measured budget while the event log keeps every event, and a late event is labelled late and kept in History. A finite effect is separate from durable task state: the state stays shown after the effect ends.

**Reduced motion** and **Still** replace motion with static trails, labels and receipt changes. Pausing decoration never pauses observation, and motion and tint supplement the text and state labels without replacing them. On disconnection the last observation freezes with its age, and ambient motion must not suggest fresh work. The map needs no per-pane poller and no model turn.

#### Allowance masthead

The masthead is the UI's one header. It holds the Field guide button, which opens the concise in-UI guide, and in that same header one horizontal allowance row: a Claude group with **Session**, **Week** and **Fable**, then a Codex group with **Week** alone. Fable is part of the Claude allowance, not a third provider. Codex has one allowance, the weekly one, so there is no Codex Session bar. Labels and bars sit side by side on a single line, with nothing above or below anything else, and no second header is added for usage; when the row does not fit it scrolls horizontally instead of stacking. A reading without a supported observation shows unknown: Fable stays unknown until a supported reading exists, and no window or amount is invented for it. Freshness and measured, estimated or unknown status open on disclosure. The readings are the shared provider observations of `dispatch` [metering](#native-rebuild-contracts); token counts are never turned into allowance percentages.

There is no capacity strip, slot count or capacity page: the only capacity the UI shows is Claude and Codex allowance. This is a display rule. It removes neither the configured resource guards in [admission](#effective-policy-and-resource-admission) nor a project's own test-environment scheduling.

#### Session dock and reader

The dock is the live Hive session: the same supervisor conversation that an external terminal reaches, never a second one. It stays mounted across every view change, keeping its connection state, draft and scroll position, and it resizes by pointer or keyboard. Text typed there is an ordinary instruction: it goes through the Hive's intake and the Imperative's [admission](#admission-checks-the-imperative) like any other, and the map, allowance and freshness displays never dispatch work on their own.

**Read Hive** is the optional reader beside the dock, for reading the Hive's messages without working from the small dock. It shows the Hive Mind's question and the Hive's reply as readable text, with attachment and artifact links, from the same session's messages. It is nonintrusive: a quiet unread count is its only announcement, and a new message never opens the reader, takes focus or moves a reader who is on earlier text. **Latest** catches up; **Close** keeps the reading position and returns the space to the map. Opening it neither navigates away, moves the map camera nor disturbs the dock's draft. The reader has no composer: the dock stays the one input. Read and unread are display state; reading a message acknowledges no decision and releases no hold.

Dock and reader both consume the same-session adapter that `dispatch` qualifies under [session launch and restart](#native-rebuild-contracts): one supervisor conversation and generation; ordered, stable message IDs with role, text parts, streaming revision and completion state; attachment links; and durable input receipts. One canonical input queue orders concurrent clients, so text sent from the dock and from an external terminal has one sequence. Pending approvals, reconnect and history retrieval work without duplicate turns and without a model call made only to read. No answer is synthesized from command acceptance, routing receipts, terminal escape sequences or map state. Attaching to an already running interactive session is qualified separately from a supported headless stream; where it cannot be qualified, the supervisor's session mode and its terminal view are designed together rather than replaced by a second conversation. Claude and local Codex each need their own versioned proof. Control of worker endpoints through `hive-send` and `hive-control` stays separate from the supervisor conversation.

#### Decision cards

A decision card presents one Mind's word that the Hive Mind owes. One card component serves them all: in **Waiting on you** and beside a [Review](#review) artifact, with the same projections, question bindings and `word` intake. A card shows its origin and puts the recommendation first, then the alternatives and their consequences. Every card takes free text, with or without a selected option, and the text keeps its full meaning, including when it qualifies the option chosen. **Later** asks for a revisit date and records it; the held work stays unresolved, and a deferral is never approval. The dated hold then appears in [Scheduled](#scheduled) as a revisit, not as a schedule that runs. The card keeps the Hive Mind's earlier words, any later amendment or supersession, the owner's reply and the resulting disposition.

Selecting and typing are drafts; only an explicit submission is an answer, under the commitment rule in [Review](#review). The card shows receipt of an answer separately from the release or completion of its hold. A stale or incomplete card cannot submit.

**Waiting on you** lists only the decisions the Hive Mind owes. Work held on a time gate, an order, a lift condition or a fold is a different kind of hold: it shows as blocked, with what it waits on, and never as a decision. An imported hold with no question is neither: it shows as a hold on its item, held with no question yet, and becomes a decision card only once a question is raised. Open decisions never pace the rest: work that no decision gates is dispatched as it becomes ready, however many calls are waiting.

A spend ask is an ordinary decision card, raised only when an action with extra cost needs the Hive Mind's permission; it states the amount and the reason. Routine use of the existing subscriptions raises none. There is no spend page, purchasing capability or standing spend authority.

#### Scheduled

A schedule is the time-gated or recurring run of one Pool item: the work of a project and its Fleet that the clock gates, such as a nightly test run, a nightly upstream digest, a Pool item gated behind a date or the Hive's own configured maintenance cycle. **Scheduled** is the view of schedules. The item a schedule runs is a Hunt, or a Prey that is a single Hunt; a Target, which has no worker, is never filed on a schedule. It opens on demand and closes with Back like every other view outside home, and it reads records written by the owners below: the Hive has no scheduler whose memory a view could read, and no model turn waits on a clock.

**What it shows.** Scheduled opens at the scope it was reached from: the Expanse from the Fleet index header, a Sector from its Fleet row, and a Subsector from its row or its selection. At Expanse scope it shows the Hive's own projectless schedules together with every Fleet's summary. Three panes share that scope and one timeline.

| Pane | Contents |
| --- | --- |
| Next up | What the Hive will run next in this scope, in due order. Each entry is a schedule's run, a dated hold's revisit or a temporary rule's expiry, named as such, with its owner, due time, the source record's freshness and the time of the Shadow's last due check. The order is the recorded next due times; the view computes no schedule of its own. |
| Schedules | Every schedule record in scope: owner, item, kind and timing, state, next due time, last run with its result and the receipt that establishes it, and missed or skipped due times with their reasons. A one-time gate and a recurrence are told apart, and a retired schedule stays listed for its configured retention with the reason. |
| Temporary rules | Every rule in force in this scope that carries an expiry or lift condition: its one rendered rule line, scope, the rule it changes, start, expiry time or lift condition, who applied it and its state, with the Hive Mind's exact words on disclosure. Rules inside the configured expiring-soon window are marked. A rule past its expiry time with no receipt reads expired, unrecorded; a recently expired or lifted rule stays listed for its configured retention with its receipt. |

Freshness and coverage follow the [record model](#record-model): every entry shows its source revision and freshness, a Fleet whose summary is missing or stale appears as incomplete coverage beside the known entries, and an empty pane under full coverage is the only all-clear. The map's Sector or Subsector filter narrows the lists; a Hive-owned schedule and a Fleet's gap stay counted. Times are recorded in UTC with the schedule's declared zone and shown in the operator's zone, and a recurrence declared in a zone keeps its wall-clock time across a daylight-saving change.

Scheduled changes nothing. Running a schedule early, holding it, ending a recurrence or extending a rule is an ordinary instruction through the Hive's intake, which resolves the real owner and records the receipt; the view then shows the bound result. A schedule held for the Hive Mind's decision is an ordinary Mind's word and appears in Waiting on you; Scheduled shows the hold, never a second card.

**The schedule record.** The `dispatch` package owns it, through `hive-schedule`, beside the execution record. The supervisor that files a time-gated or recurring Pool item registers its schedule through `hive-schedule file` before reporting the item filed; an item with a date and no schedule record reads unregistered, never scheduled. One record serves a schedule for its whole life: a recurrence keeps its identity across runs, and each run is a new execution generation of the owning item with its own execution record and receipts.

| Field | Required content |
| --- | --- |
| Identity and owner | Stable `schedule_id` and `schema_version`; owning `home_id`, `workspace_id` and `project_id` where the work belongs to a project, or the explicit projectless scope of the Hive's own operational work, in the form the [execution record](#components-and-private-state) uses; the owning Pool `task_id`; the registered parent route. |
| Kind and timing | `kind`: `gate` for a one-time not-before time, or `recurrence` for a period and its anchor. The timing as declared, with its time zone and revision. |
| Item to run | The Pool item by identity and revision, with its accepted Imperative and specification revisions, dispatch class and delivery axes read from that item. The schedule stores references, never a second editable copy of the criteria. |
| Timing | `next_due`, a time computed and written by the dispatcher at filing and after each run; the due times missed while no owner was available, and the due times skipped because the previous run was still running, each with its reason. |
| Last run and result | The last execution generation, its launch time, its result and the receipt that establishes it, by reference: launch, collection, Synapse or landing receipt as applicable. A verified termination (finished, failed or stopped) is the only result that ends a run. A run whose state cannot be observed stays `running` with its result unknown, and an unknown execution is never terminal. A result is a receipt; a worker printing done is not one, and a schedule with no collected result reads unknown. |
| State | `scheduled`, `due`, `running`, `held` or `retired`, with the receipt and time that set it. `held` names its hold: a Mind's word, a policy or resource park, or an instruction. `retired` names its reason: a gate run once, a recurrence ended by instruction, or the item archived. |
| Provenance | Who filed or changed the schedule, by intake receipt and revision: the Hive Mind's instruction, or the supervisor within its recorded authority; and the writer's version. |

**Who writes it, and when.** The dispatcher writes the record when the item is filed with its gate or recurrence; when the Shadow's due wake is drained (`due`, with the due time it answers, only while the schedule is still `scheduled`, the wake's schedule revision and due occurrence match the record, no launch is already recorded for that due occurrence, and no generation is running or unresolved, checked and written in one atomic transition; a wake that fails the check is recorded as handled with its reason and changes no state, so a held or retired schedule is never made dispatchable by a late wake); when it launches the item (`running`, binding the new generation); when the execution record reaches a verified terminal state (the result and its receipt are recorded and the current `held` or `retired` state is preserved; only a schedule still `running` then returns to `scheduled` with the next computed due time for a recurrence, or becomes `retired` for a gate); and when a hold, park or instruction changes the state. An unresolved generation, one whose termination is unverified or unknown, is held for reconciliation: it advances neither kind of schedule. A due time is a trigger, not authority: the launch goes through the Imperative's [admission](#admission-checks-the-imperative), the policy resolver and the resource floors like any other dispatch, and a refused or parked launch leaves the schedule `due` or `held` with the reason. A recurrence whose previous run is still running or unresolved launches no second run; that due time is recorded as skipped with the running generation named. A recurrence missed while the Mac was unavailable runs once when its owner drains the wake, with the missed due times recorded; missed periods never queue a burst of launches.

**How due work is noticed.** The Shadow's existing bounded tick compares recorded due, revisit and expiry times with the clock and writes one durable wake per record, schedule revision and due occurrence, under the [Shadow's cadence](#the-shadow); no always-on scheduler, timer process or waiting model turn is added. A wake and its handled receipt are keyed by the record, its schedule revision and the due occurrence they answer, so a schedule edit that keeps the same due time yields a fresh wake and an old wake is never taken for it; a launch is keyed by the schedule and due occurrence alone, so no revision change launches a second run for one due occurrence. The owning supervisor drains the wake, reconciles current truth and acts once: it dispatches a due schedule's item, re-presents a dated hold's question, or records a rule's expiry; a wake that no longer matches current truth is recorded as handled without effect. The Shadow's own poll cadence, backoff and reconciliation are observation configuration and do not appear in Scheduled.

**Dated holds.** A decision deferred with Later carries its revisit date in its `word` record, and Scheduled lists it under Next up as a revisit with the question and its owner. Reaching the date wakes the owning supervisor, which re-presents the decision card and may mention it in the Hive session; nothing is launched, the held work stays held until answered, and the deferral remains unresolved. A dated hold is not a schedule record, has no run or result, and leaves Scheduled only through `word`'s release or completion receipt.

**Temporary rules.** A rule with an expiry or lift condition is the same rule record as any other, written by `pool` under [standing rules](#definitions-standing-rules-and-generated-knowledge); Scheduled presents it and the Shadow notices its expiry time. The resolver stops applying it at its expiry time whether or not the expiry receipt has been written. The receipt, written by the owning supervisor through `hive-rule expire` when the Shadow's wake is drained, records that the expiry was noticed and honoured; a missing receipt shows in the pane as an unrecorded expiry, never as a rule in force. A lift condition is honoured by its named receipt and shows as in force until that receipt exists. A generation dispatched under a temporary rule keeps the receipt it was dispatched with; expiry changes later resolutions only.

#### Record model

These are logical requirements; package owners settle serialization during contract work. Every projection identifies its schema and source revision, owning home, freshness, coverage and replay cursor. Project-bound records also identify workspace, project, clone where relevant, task and execution generation. Every mutation carries its expected revisions, correlation and idempotency identity and authority reference. A display can be incomplete without becoming an authoritative empty result.

| Record family | Authoritative owner and binding | Presentation |
| --- | --- | --- |
| Workspace, Fleet and project registry | `dispatch` provisioning with durable `pool` references: workspace, Fleet home and charter, parent, project registrations and clones | Sector and Subsector selection and the Fleet index; an unavailable parent or child projection shown as such |
| Pool, Imperative and specification | `pool`: one owning task, criteria and Imperative revisions, dependency and handoff links | Pool and the task inspector; no second editable copy of the criteria |
| Targets, Prey and Hunts | `pool`: Pool items at three levels linked by parent edges, the roadmap order from each Target's Wave and blocked-by edges, and the derived landed fact of a Target and of a Prey that holds Hunts | The Pool and the task inspector show a Target with its Prey beneath it and a Prey with its Hunts, counted as landed of drawn; a Target's Prey are counted by column in the screen's words, for example 2 captured, or 1 confirming and 1 not started, not as landed of drawn; a Target or a multi-Hunt Prey is never shown with a worker, a place or an Imperative |
| Execution, delivery and holds | `dispatch`, `synapse` and `word` over Pool identity: three separate axes, adapter and generation, actual observations and evidence | Task planets and the inspector; a hold can coexist with running, ready, stopped or unknown |
| Session and messages | The `dispatch` session adapter: session and generation, message ID and order, role, text parts, streaming revision and completion, attachments and input receipts | The dock and Read Hive |
| Instructions, steers and control | The owner's durable accepted, routed, delivered, acknowledged and lifecycle receipts, with the exact message or Imperative revision and destination generation | Receipt stages and map effects; a Fleet's acknowledgment never stands in for a worker's |
| Decisions and review rounds | `word` decisions; `ui` registered artifacts, feedback and replies; `shadow` observation and routing receipts | The one decision card, with exact words, question revision and attachment completeness; accepted, released, completed and Done as independent states; a Later revisit date also lists in [Scheduled](#scheduled) as a dated hold |
| Policy | `dispatch` effective scoped policy and validated request receipts, with expected and current revisions and the source-rule digest | The Swarm's inheritance view, Accepted and Applied; a conflicting update stays unapplied |
| Schedules | `dispatch`: the [schedule record](#scheduled) over Pool item identity, with kind and timing, computed next due time, missed and skipped due times, last run generation and its result receipt, state and the receipts that set it | The Scheduled view, the next due entries of the Fleet index and the due marker; nothing is computed from a timer, and a missing Fleet summary reads as incomplete coverage |
| Temporary rules | `pool`: the rule record with its exact words, scope, the rule it changes, effective time, expiry time or lift condition, applying authority and the expiry or lift receipt; `dispatch` policy receipts carry the rule digest that includes or drops it | The temporary-rules pane of Scheduled; in force, expiring soon, expired, lifted and superseded read from the record, and an expiry past its time without a receipt reads expired, unrecorded |
| Allowance and context | `dispatch` provider and session observations with accuracy and freshness, projected through `shadow` | The four allowance fields and each Fleet's context percentage |
| Source health and handling | `shadow`: registered source identity, observation time, next due time, last observed cursor, durable wake and routing, handled cursor | The freshness signal, unhandled wakes and the true age of the last handled sequence; a fresh poll never resets that age |
| Synapse, Harvest and landing | `synapse`: repository, full URL, base and head, check and reviewer producers, finding dispositions, ready and landed receipts | Harvest detail and head-bound map markers; invalidated proof turns stale |
| Correlated events and History | The owning package's event ID, source and home sequence, scope, task generation, correlation and causation IDs, occurred and observed times and source revision | Finite map effects and History; projection gaps and late delivery stay explicit |

The UI reads only projections routed to it. A Fleet observes its own private home and reports summaries through its registered parent channel; the Hive never sweeps another home's endpoint namespace to fill a view. Each parent projection names its owning home and workspace, the applicable project, its expected source membership, revision, cursor, coverage and freshness. A missing or stale child summary is shown as incomplete coverage: the Mind's word badge shows the known calls plus the gap, the freshness signal counts every registered source, and neither reads all-clear from an absent child or a filtered list. A cursor gap is recovered from a bound snapshot and the changes after it, without duplicating events. Identical short IDs in different homes never select an owner: an answer routes to its original home, task and question revision through `word`.

Records update live, and a stale or disconnected state is always shown as such. The transport is an implementation decision: the requirement is actual-record updates with bounded observation and recovery, and no manual export step keeps a display current.

**Published records.** For each project it runs, Hive publishes three records for an outside viewer of its projects, and nothing else: the project's delivery posture, the export of the decisions the Hive Mind owes, and the roadmap. The export holds the decisions the Hive Mind owes and no other kind of hold. The roadmap is the projection of the project's Target items in Wave order, each Target with its outcome, the Hive Mind's words on it, the Targets it depends on, any act of the Hive Mind beside it, and its revisions and events; it carries no definition for the viewer to accept. Each record is a projection with its source revision, never a second store, and the viewer takes no dependency on Hive's code, tooling or interface. The three records are for the operator alone: each is a file written into the operator's own account on the machine Hive runs on, readable by its owner only; Hive serves them to no one, and they never enter a repository, a Harvest, a comment or a log. They carry what the operator's own viewer needs to show them their projects, the Hive Mind's own words and acts included, and never a secret value or home credential. No other reader exists: showing any of it to anyone else, a collaborator or another account, would be a new decision of the Hive Mind's with its own choice of fields, and until one is made the records have one audience. The login of Hive's own UI server, described under Serving and login, is a separate matter and is not what protects these files. A sentence typed to the Hive through the viewer is an ordinary instruction through the Hive's intake; an answer that arrives through the viewer's hold route enters `word` like any other channel; and a press in the viewer that starts a Target is optional and never a gate: once the Hive Mind has told the Hive to work on a project, the owning Fleet dispatches each ready Target and Hunt as its predecessors land, and a press authorizes only the pressed Target's current definition and its Prey.

#### Review

Mockup and design review live in `ui`, replacing Lavish. A Lictor writes a mockup as plain HTML into the owning supervisor's private home, one file per revision. The Hive Mind opens it from a link in the Hive session or on a decision card; there is no permanent Review tab. The artifact surface shows the mockup with annotation controls and the decision cards beside it, and **Back** restores the previous view, scope, selected task, map camera and session draft. The session dock, and Read Hive with it, stay available throughout. The owning Fleet, or the Hive for its own task, receives each submitted round through the Shadow and owns its handling; the Hive Mind manages no review workflow. Automated code review and fix rounds remain Synapse's.

The decision cards beside the mockup and the cards in **Waiting on you** are one component, the [decision card](#decision-cards): the same projections, question bindings and `word` intake.

**Files and ownership.** All paths below are relative to the selected private home, outside every project repository. A review lives under `reviews/<task-id>/<generation>/<review-id>/`. Its record binds home, workspace, project where the task belongs to one, task, generation, review, owning supervisor and assigned Lictor; the Hive's own projectless work declares that scope explicitly. IDs and the registered parent route decide ownership: a matching short name or a selected filter never picks another home. Revision and round numbers increase independently and are never reused.

| File | Contract |
| --- | --- |
| `review.json` | Versioned review identity, owner and Lictor references and registered parent route; the manifest of each revision's HTML and assets with relative paths and digests; current revision and round; completion-record reference. Publish a new current revision only after its complete files and any reply to the previous round are durable. |
| `revision-0001.html`, `revision-0002.html`, … | Immutable plain HTML revisions, one file per revision. Referenced assets live in revision-specific paths under the review directory with retained digests; a later revision cannot overwrite an earlier revision's assets. |
| `round-0001.feedback.json`, `round-0002.feedback.json`, … | Exactly one feedback file per round, containing the round's bindings and its ordered operator events: drafts, submissions and Done. The `ui` feedback writer preserves earlier events when atomically replacing the file under the review lock. |
| `round-0001.reply.json`, `round-0002.reply.json`, … | The Lictor's reply to that round, binding each response to the original note, event and question IDs and identifying the next revision and its digest where one was written. Operator words remain in the feedback file unchanged. |
| `final.json` | The final review record written by Done, bound to its event, the reviewed revision and the durable feedback sequences it includes. It records completion of this review, separately from decision, implementation and task completion. |

**Serving and login.** The `ui` server is read-only for artifacts. It binds to loopback for local use, where the local operator's home-bound UI session is the login, or to the operator's existing tailnet interface for private remote use, where the operator's verified private network identity is the login, scoped to the selected home. A client-supplied identity string or header is not authentication, and the identity path is itself qualified before remote use. The UI session's own authentication material is not an enrolled secret and is no Spoor: it is minted in memory by the server for its own use, bound to the selected home and the login above, never written to a record, a file or a log, and never shown; whether it outlives one run of the server is a product choice that changes none of this. No login of the UI holds, shows or accepts a credential value: credentials are under [Secrets](#secrets-hive-keeps-none), and the enrolment status surface is the UI's one view of them. There is never a public listener, and no tunnel, public host, separate review product or Hive-managed network setup is required. Tailnet access is optional operator infrastructure, so loopback use keeps the six-dependency profile.

Any artifact file in the home can be served once its owner registers it in a review's manifest, and nothing else in the home can: a private home is not a web root. The server resolves a registered review and revision to its immutable manifest and serves only that HTML and its declared assets, after validating path and digest inside the review's own directory. It refuses traversal, symlink escapes, undeclared sibling files and any path outside the manifest. Registration is an owner operation; nothing typed or selected in the browser widens it.

**Overlay and isolation.** The server injects the annotation overlay's in-page helper into the served copy of the page, never into the revision on disk. With it the Hive Mind clicks an element or selects text; notes are typed and decision cards pressed in the trusted UI beside the mockup. Artifact content runs in a distinct origin or an opaque sandbox, and is never given a permission combination that lets same-origin scripts escape that boundary. The helper is an untrusted bridge: the UI validates the sender, channel, review and revision binding, shape and size of every message from it, and no message from an artifact can authorize a decision, read the UI session's authentication material, which the server keeps in memory and never hands to a page, imitate the trusted controls or submit an authenticated answer; a Spoor or a value is never among what a page can read, under [Secrets](#secrets-hive-keeps-none). The feedback writer is a separate, narrowly scoped `ui` writer for the registered round's file; it is neither an arbitrary file-write endpoint nor a Pool writer. Trouble rendering an artifact is never a reason to weaken this boundary, and neither the UI nor ordinary artifact review depends on the optional browser automation stack.

**Capture.** Everything the Hive Mind presses or types lands in that round's one feedback file, in the exact words typed: element clicks and text selections, notes, option presses, typed answers, Submit round and Done. Text is kept exactly as typed, including whitespace, and each amendment is kept rather than replaced by a summary. The surface asks for no credential, and a value is never an input to it. The `ui` feedback writer runs the owner's no-value check of [Secrets](#secrets-hive-keeps-none) on every event, note and card answer before the first byte of the feedback file is written: what it recognizes it refuses whole, with a precise failure and nothing written, never redacted, truncated or reflowed; what it cannot recognize is kept exactly and is a found copy from the moment it is found, and it reaches no Spoor and no launch.

Clicking, selecting, typing and choosing an option record **draft** events. Drafts may be persisted in bounded batches, and the page shows input as unsaved until the writer acknowledges it durably. A draft sends nothing to `word` and gives no worker anything to act on. Size and retention limits never drop the Hive Mind's words or acknowledged history: under pressure the writer refuses with a precise failure instead of truncating or reporting a save that did not happen.

**Submit round** is the commitment boundary. It commits, against the displayed question and round revisions, an immutable snapshot of each answered card (its selected option, if any, together with the exact text typed with it) along with the round's notes, free-standing instructions and attachment manifest. An option followed by a qualifying note is one answer; an option alone is never applied ahead of its text; free text without an option is a complete answer. Cards left unanswered stay open. A changed revision or a conflicting concurrent submission returns a visible conflict rather than overwriting a newer answer, and a stable request ID makes a retry idempotent. The writer acknowledges a submission only after the snapshot is durable, returning its event ID and sequence. A committed card answer and the submitted round pass the same no-value check as a note, before their first byte, under [Secrets](#secrets-hive-keeps-none); an answer the check refuses is not committed and the card stays open. Feedback capture is a receipt, not a ruling: the page shows `word`'s acceptance and the hold's release or completion separately, and a stale or incomplete card gains no decision authority by being written to a feedback file.

Each feedback file carries `schema_version`, `home_id`, `workspace_id`, `project_id` where the task belongs to a project, `task_id`, `generation`, `review_id`, `round_id`, the owning supervisor and Lictor references, and the reviewed revision's path and digest. Each ordered event carries the fields below that apply to its kind; fields that do not apply are explicitly absent.

| Field | Required content |
| --- | --- |
| Identity and order | Stable `event_id` reused on retry, monotonically increasing `sequence`, capture time, durable receipt time and the authenticated operator reference. |
| Kind and words | `kind`: a draft (`target`, `note` or `card-draft`), `submit` or `done`. The exact `text` and the exact label of any control pressed. A note keeps its stable `note_id` across edits. A free-standing round instruction is its own entry, never recast as a card answer. |
| Annotation target | The reviewed revision and digest, the element locator and captured element text; for a selection, its exact quoted text and start/end DOM paths and offsets. The original target is kept even when a later revision moves or removes the element. |
| Card binding | Card, question, held-item and decision-round IDs and revisions, owning home and task, the selected option ID and displayed label if any, and the typed answer verbatim. These keep the review round distinct from the decision round it presents. |
| Submission binding | For `submit`: the expected round revision, the last draft sequence it includes, and the immutable snapshot of each committed answer (option and qualifying text together), the round's notes and instructions, and the attachment manifest. |
| Completion binding | For `done`: the displayed revision and digest and the last feedback sequence included in the final record, with submitted answers told apart from saved but unsubmitted drafts. |

**Wake and route.** On its bounded local tick and on recovery, the Shadow reads the registered review files in its own home for sequences beyond its durable cursor, including retained rounds that receive a late submission. It records the observation and, for a submitted round or Done, the wake before advancing that cursor, then wakes the recorded owning supervisor. Draft events advance observation only: they wake no model and mark nothing handled. The supervisor collects the complete submitted round, with all its text, notes, questions, bindings and attachment fetch outcomes; a missing, truncated or unreadable part keeps the round incomplete, and nothing in it is ruled on until it is whole. It acknowledges handled sequences only after recording routing receipts.

Committed card answers go through `hive-word answer`, the one intake for the Mind's word, with the exact words and the original question and decision-round revisions. A valid answer releases the corresponding hold or completes the question exactly as a chat answer would; an answer to a changed question stays held for reconciliation. Submitted notes and free-standing instructions go verbatim, with their annotation targets, to the assigned Lictor through the supervisor's durable `hive-send` steer; they are instructions for the round, never read as an answer to whichever card was visible. If the Lictor has stopped, the supervisor keeps the steer for an authorized continuation: delivery does not depend on a live session, and a closed page neither relaunches a worker nor widens its scope.

**Next round and Done.** The Lictor reads the round, writes its reply file and, where a revision was asked for, the next HTML revision, then publishes the new current revision through `review.json` once those files are durable. The page picks up the change from its live projection and reloads the mockup. The round just answered stays beside it as the latest round, its notes with the Lictor's replies, linked to their original revision and targets rather than silently reattached to changed elements. New feedback goes to the next round's file. Neither a Lictor nor a supervisor needs to be running while the Hive Mind reviews.

**Latest round first.** The surface shows the latest round and nothing older open. The latest round is the last round with a submission, together with the Lictor's reply to it where one has been written; before any submission it is the current revision alone, unless the first round already holds a settled card, which then makes the first round the latest. At the top of the surface are the current revision; the latest round's results, that is, each of the Lictor's responses beside the note or card it answers, shown as a decision card or as a recommendation with a picture of the element it concerns where one helps, or the round's submitted notes awaiting that reply; and every open decision card. Every earlier round is collapsed under its round number at the bottom of the surface, in round order, and opens only when the Hive Mind expands it: none is open by default, and expanding or collapsing a round is display state that writes no event and changes no record. An expanded round shows its own notes, replies and the cards it settled exactly as recorded, read from that round's feedback and reply files and `word`'s projections; there is no second store of rounds, and collapsing is not archiving: the files stay durable, so collapsing hides nothing. An unanswered call never collapses. A card raised in any earlier round stays among the open cards at the top until answered or explicitly superseded, regardless of age, and only then takes its place under the round that is the latest when its settlement arrives. An answer given by a round's submission stays as written under that round, which is then the latest. An answer or supersession that arrives another way, through the Hive session, the CLI or Waiting on you, files under the last submitted round at that moment, read from the order of the current round in `review.json`, the per-round feedback and reply files and `word`'s receipts: it shows settled with that round while it is the latest and collapses with it under its number once a newer round is the latest. Where no round has been submitted, it files under the first round, and a round that holds a settled card is shown from then on, at the top until a later round is the latest and collapsed under its number after that, whether or not it ever receives a submission. A settled card therefore never files under a round the surface does not show, and stays reachable in every sequence, including Done with no further submission.

Pressing **Done** ends the review. It persists the Done event in the current feedback file, then writes `final.json` with review, task and generation identity, operator and time, final revision and digest, the round sequences included, reply references and the known decision receipts or pending holds. A crash between those writes is recovered from the Done event, and the page reports completion only after the final record is durable. Done never turns a draft into an answer: text typed but not submitted is listed in the final record as unsubmitted. Done supplies no missing card answer, closes no hold, accepts no implementation, completes no task and authorizes no Assimilation.

**Durability.** Rounds, replies and completion are files, not a live listener's memory. Saved input survives a dead Lictor, supervisor or UI process, and a restart replays pending submitted feedback through the same event IDs and routing receipts. A late answer is still persisted against its original round and read, even after a new revision, a worker's exit or Done; `word` reconciles its question revision before applying it, and `final.json` stays the snapshot of what Done included. Closing or archiving a review discards neither an unanswered decision nor unread feedback, and ending the page closes no decision: the owner still inventories the remaining operator decisions before the originating report is complete.

**Sharing.** Export the selected HTML revision as one standalone file with its assets inlined. The export holds the mockup only: no private feedback, decision records, Spoor or authenticated connection back to the home, and no credential value, of which the home holds none under [Secrets](#secrets-hive-keeps-none). Sharing that file needs no public host or tunnel, and the review history stays in the home. This export is unrelated to how live records reach the UI.

## Components and private state

Hive combines instructions, skills and seven internal packages with the Pool and Spawning Pool adaptations and six core dependencies specified in [Tooling](#tooling).
It needs no new hosted control service.
The `hive-*` command names below are **proposed interfaces**, not installed commands or vendor flags.
Their upstream owners are named so an implementation can port behavior without reproducing it in several places.

Each supervisor has an explicitly selected private home outside every project repository: the Hive has its own, and each Fleet has one for its workspace, shared by the projects registered there, which keep distinct project and clone identities. The following are logical stores within that home, not machine-specific locations. Use atomic record replacement, append-only event journals, and home/task locks. Missing or malformed authoritative records stop the affected mutation; a cached display cannot authorize it. No store below holds a credential value: each holds at most a Spoor, under [Secrets](#secrets-hive-keeps-none), and its writer validates that before a temporary file is opened.

Execution, delivery, and decision state are separate. Execution can be planned, launching, running, stopped, failed, or unknown. Delivery can be unpublished, collected, Harvest-open, in-Synapse, ready, assimilated, or retired. Holds can coexist with any of those. An event saying `done` does not imply Assimilation, and a later `working` event does not close a keyed decision.

### The Pool and the Mind's word

Pool items describe work, never persistent agents. A Fleet's routed work belongs in its Pool, with its project identity wherever the work belongs to a project; the parent keeps a handoff receipt rather than a second competing task. Dispatch atomically records its configured local resource reservation and the launch attempt when it transitions a queued item; that bookkeeping cannot reserve a vendor allowance, which is not bookable, or guarantee future provider availability. If submission becomes uncertain, retain the reservation until reconciliation proves what happened. An item's not-before date or recurrence makes it the owner of a [schedule](#scheduled): the item remains the one owner of the work, the dispatcher's schedule record carries the timing and its runs, and a date on an item never dispatches it by itself.

A Pool item has a level: target, prey or hunt; a decision held for the Hive Mind has none. Work larger than one bounded item lives on its project's roadmap as a held Target, recorded as a Pool item of level target in the Pool of the Fleet that owns the project, or in the Hive's Pool for the Hive's own stages. A Target is a Pool item that never dispatches. It carries its outcome as its title, the Hive Mind's words as its body, its Wave, the Targets it depends on as blocked-by edges and, once its define step has landed, the accepted definition, and nothing else: no Prey, Hunts, files or size until its define step draws them. Its Prey point at it with a parent edge, a Prey's Hunts point at the Prey the same way, and a parent edge points nowhere else. A Target and a Prey that holds Hunts have no Imperative, no generation and no place, and a transition that would set their state directly is refused: the Pool derives landed for a Target when it has Prey and every one of them is done, and for a Prey when every Hunt beneath it is done, exactly as it derives blocked, held and ready at the moment of a read; since the landing of a Target's last Prey cannot be Assimilated without the project's long-test result, a Target cannot read landed without it: the Synapse receipt where that landing's validation is Synapse, the stated checks' result on the direct route. A Prey without Hunts is dispatched itself. The define step is dispatched as work of its own that names the Target it defines through a discovered-from edge; it is not one of the Target's Prey, and its landing is what gives the Target its definition and its Prey. An act of the Hive Mind beside a Target is a Mind's word held on the Target before its define step, or on the Prey or Hunt it gates after. A schedule is filed on a Hunt or on a Prey that is a single Hunt, never on a Target. The roadmap Hive publishes for a project is a projection of that project's Target items in Wave order, never a second store. Prove that a Target with Prey reads landed only when the last of them is done and that a Target with none never reads landed; that a transition to done on a Target or on a Prey that holds Hunts is refused, and so are an Imperative and a generation for either; that a parent edge from a Target, or into a Hunt, is refused; and that the roadmap projection follows the Waves and blocked-by edges of the Target items with no record of its own.

An operator decision is an ordinary Pool item held for the Hive Mind; routine technical acceptance within approved scope belongs to the owning Fleet. Prefer holding the work it gates; create a separate question only when it has its own scope. Record the question, consequence, recommendation, alternatives, the exact free-text answer given with or without a selected option, and any explicit revisit date privately. Present the recommendation first; Later records a revisit date without resolving the held work. The dated hold lists in [Scheduled](#scheduled) as a revisit, and reaching the date re-presents the question without running anything. A spend ask is this same ordinary card, raised only when an action with extra cost needs the Hive Mind's permission and stating the amount and reason; there is no separate spend page or purchasing capability. `hive-word answer` records the actual answer and either releases the work or completes the question. Replays of the same answer are idempotent; conflicting answers require reconciliation. A deferral date is not approval.

Before completing a Lictor report, the supervisor inventories every remaining operator decision and records the held items, or explicitly records that there are none. Finishing the report and closing those decisions are distinct actions. Cleanup must retain an open question even when its source report or Harvest has been delivered. This ports the [held-task lifecycle](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/docs/captain-hold-lifecycle.md).

### Definitions, standing rules and generated knowledge

A Target passes through definition needed, defining and defined, and from then on is building while any of its Prey is open and landed when all of them are done; its Prey and Hunts pass through queued, in flight and done with holds kept separately. On screen, building reads Hunting, a Prey awaiting its validation reads Confirming, and landed reads Captured; these three are display words only: the record states and the Pool contract's derived facts keep their names, building and landed, and no contract changes for them. The Fleet commissions only the needed definition work; the define step draws the Target's Prey, each with a title and an explanation, deliverable on its own and parallel where possible, with Hunts a, b, c under a Prey where it needs them, and never a split by size alone; it names the contracts the dependent Targets read and lands them in the Target's earliest Prey, and it lists in one line each what it leaves undecided. A Target's define step starts when the contracts its definition reads are on main, never from a predecessor's draft, whether or not the predecessor has finished building; a follow-up, a residue fix, a relaunch or a Lictor is dispatched from its filed record and owes no define step. The Fleet accepts the definition itself against the already authorized intent and starts its Hunts on its own authority; of a definition, only a change to what the Hive Mind sees reaches the Hive Mind, on a page with real screens, before it is built, and only a genuine product ruling reaches the Hive Mind from a define step. A definition that a later ruling or landing falsifies is amended in place by its owning Fleet before the next Hunt it covers starts, while a Hunt already running finishes on the definition it was dispatched with. A Hunt is one build group sized, where its validation is Synapse, to one Synapse run, proving in its ordinary validation its build, the test targets it touched and its own long runs and not the project's full suite; the landing of the Target's last Prey carries the project's long tests under the [proof-scope rule](#checks-and-review-contracts), on either delivery route; a Hunt that keeps asking for files outside its grant was drawn too wide, and the remainder is split rather than the grant widened. A finalizer on an integration branch is a choice the definition names only for Hunts that cannot land apart, never the default, and no Target is bounded by a count of Hunts or files. A sufficiently complete existing specification can be referenced directly; this is not mandatory planning ceremony for every small task. The acceptance receipt identifies the Fleet's supervisor, specification digest, admission revision and open product questions. A product choice returns to the Hive Mind; technical acceptance cannot settle it. Build dispatch refuses an unaccepted required revision, and later edits invalidate only affected acceptance/evidence rather than silently changing the worker's target.

The private rule store separates original words from their operational interpretation. `hive-rule record` appends immutable words and origin; `amend` adds an attributed revision or supersession without rewriting history; `resolve` computes rules effective for the current home, workspace, project where applicable, role and time, preserving Hive → workspace → project inheritance and the priority of an explicit task instruction within current authority. Each rule carries authority, scope, status, effective/expiry times, source references and requirement/evidence links. An unresolved conflict holds the action it affects. Expired waivers, archived narrative and abandoned trials remain readable but are not loaded as current policy. A missing render field is not proof that a rule was retired. A rule of the workflow itself is recorded at the Hive's scope and inherited by every Fleet; it is never recorded for one project. Whatever would change the workflow, add to it or remove from it is reviewed by a Lictor against the current workflow first, and the change is applied with that review in hand; a rule the Hive Mind states is recorded at once and its review follows. Routine operation of a reviewed workflow is not a proposal to change it, and the review adds no verdict gate beside Synapse. The standing rules of the workflow that this design does not state as a mechanism are rule records at the Hive's scope, seeded when the Hive's home is provisioned and rendered into supervisor instructions by `hive-memory render`, never prose a supervisor keeps by hand.

A temporary rule is this same record with an expiry time, a lift condition or both, not a second mechanism. A waiver, a Hunt limit for a bounded period, an order to lean on one vendor until an allowance resets, a delegation of authority for one night, a policy trial from The Swarm and a bounded exception to a resource floor are each one rule record, written by `pool` through `hive-rule record`: its scope (Hive, workspace, project where applicable and role, narrowing to one task generation when the change rides an Imperative revision), the standing rule it supersedes or qualifies by identity and revision, the Hive Mind's exact words or the request text as submitted, the effective time, the expiry time or the lift condition naming a recorded receipt kind and identity, the applying authority with its intake receipt, and one rendered rule line. `resolve` excludes a rule past its expiry time by the clock, before any receipt exists, and `hive-policy resolve` therefore drops it from the next receipt's rule digest; a generation already running keeps the receipt it was dispatched with, and nothing restarts it on expiry. The expiry is a scheduled event under [Scheduled](#scheduled): the Shadow notices the time, the owning supervisor records it through `hive-rule expire`, and that receipt says the expiry was noticed and honoured. A lift condition is honoured by its receipt: when the named receipt exists the owner records the lift through `hive-rule amend`, and until then the rule binds and the view says so. Extending or ending a temporary rule early is an attributed amendment under its own authority, never a rewrite of the original words or dates, and the standing rule it changed is never edited. An expired or lifted rule stays readable with its receipts and is not loaded as current policy.

Hive owns the native specification and rule store in `pool`, with operator decisions entering only through `word`. Preserve each ruling verbatim and derive one effective rule line linked to its source/revision. Per-change acceptance criteria live on the Pool item and render into the Imperative's Standard from that same revision; a render is not a second editable source. The store retains immutable identity, accepted revisions, amendment history, proof references, atomic update/recovery and closure receipts. Failed updates leave a pending transaction with a replay key, never a fictitious completed archive.

`hive-memory render` derives shared, Fleet-specific and project-scoped instructions from the effective rule set and each fact's single canonical owner. Projections record source revisions, scope, renderer version and digest. `check` reports duplication, budget violations, stale sources and consumer drift using configured budgets; it never repairs authority by copying contradictory prose. `propagate` records what each consumer received and acknowledged. Missing propagation remains visible, and dispatch/restart refuses a stale projection when the changed rule affects its authority or behavior.

Knowledge maintenance has one writer per store and an explicit queue. Stow can enqueue uncovered knowledge under its canonical owner; folding, archiving and propagation run only under an authorized maintenance policy or an explicit instruction. Their cadence is configuration. Deferred research and held work stay in the Pool for the Hive Mind; a maintenance cycle does not authorize picking them up. Source changes produce invalidations and receipts, not competing hand-maintained rule copies.

### Complete review rounds and answers

`hive-word` handles channel-independent rounds as well as simple questions. Before marking a round read, collect its complete nested text, all questions and an attachment manifest with content revisions/digests and fetch outcomes. A missing, truncated or unreadable part keeps the round incomplete and yields a precise fetch blocker. Transport acceptance, draft persistence, submitted-round commitment, content-read acknowledgment, the Hive Mind's answer and decision completion are separate states. Only an explicitly committed answer, with its selected option and the exact free text qualifying it, enters `word`; draft edits and a review's Done cannot supply a missing answer.

One owner presents and reconciles each round through the shared decision cards in Hive's UI, whether in Waiting on you or beside a [Review](#review) artifact, or through the CLI, all using the same `hive-word` intake. The card is a scoped projection, never an independent decision store. Store the exact answer privately, bind it to the question/round revision and record a per-question disposition. Replayed events are idempotent; a changed question needs reconciliation, not silent application of an older answer. An unanswered call remains visible until answered or explicitly superseded, regardless of age. Archiving a round must preserve a verifiable answer and its completion receipt; absence from the active queue proves neither. A collected Lictor report, answered card round and completed decision have independent receipts, so none can close the others by inference.

## Secrets: Hive keeps none

Hive keeps no secret. A token, key, DSN, hook address or password lives only in the platform's secret store and is retrieved at run time into the one command that needs it. Hive never keeps a secret in a file, a config, a record, a log, a transcript or an argument list. This section is the one statement of that contract. Every other part of this document that touches a credential, or that could carry one, refers here and restates nothing; where a sentence elsewhere seems to say more or less than this section, this section governs. Hive implements the whole secrets flow natively, and on this point it does not have to stay a copy of the upstream it inherits from.

Two names carry the contract, in the vocabulary of [Vocabulary and placement](#vocabulary-and-placement):

| Name | Meaning and responsibility |
| --- | --- |
| Spoor | The durable reference to one secret. Beyond what every record carries (schema and version, identifier, revision, times and scope) it holds four fields and no other: the store, the host, the account identity and the purpose. It is neither the value nor a transferable authorization, and holding one grants no access that the holder's own host and store do not grant. A record of `dispatch`, kind `dispatch.spoor`, in the dispatcher's own records, with its own identifier prefix `spoor_`; enrolled, checked and listed through `hive-fleet`, which already owns the registry of identities a Spoor names. A Spoor's **name** is its identifier, and nothing else: wherever this document says a Spoor's name, in an Imperative, on the status surface or in an error, it means that identifier, never the account identity, which stays a field of the record. Every consumer works on Spoors, with one lookup per use. |
| Tendril | The one small audited launcher: the store-backed consumer and exec primitive, in the contract library's one process-execution path. It resolves one Spoor in the host's selected store into memory, and either uses the value in the calling process or builds a minimal environment and executes one approved short-lived program with an argument list that holds no secret. It is the only code in Hive that reads a store or sets a child's environment from a resolved value, and it sits in the launch path of every consumer that must hand a value to a program. |

The value itself has no name because it has no life beyond one use: it is an ephemeral type of the contract library, defined in Tendril's own package. Its JSON and text encodings fail with an error, so no record, response or log line can carry it; its print or debug form, which cannot fail, is one fixed redaction; neither ever contains the value.

Tendril is small and audited, as contract rather than intent. It is one implementation, in one file of `contract/exec`, and nothing else in Hive reads a store or sets a child's environment from a resolved value. It is bounded: one call resolves exactly one Spoor, sets exactly one declared variable in a child environment it builds from nothing, takes a fixed argument list, starts one short-lived process or uses the value once in the calling process, holds the value for no longer than that call, and has no option that prints, returns, logs or writes a value. Every change to it is reviewed as a contract change, under `test-contract`, like every change to the contract library. The confinement is by construction: the value type's resolving constructor and the setter of a child's environment from a resolved value are unexported names of Tendril's own package, the one process-execution path, so no other package can name them and the compiler enforces it. Prove, in `test-contract`, against the recorded fake of the store and a fake consumer: one lookup per use; exactly one declared variable in a child environment built from nothing; a fixed argument list holding no value; nothing of the value in any output, error or record; and refusal of every call outside those bounds, among them a call that sets two variables, resolves two Spoors or receives a non-fixed argument list.

### What Hive holds, and what it never holds

Hive holds the Spoor and nothing more. A Spoor is complete when it names the store, the host, the account identity and the purpose; a field for a value does not exist in its schema, and the schema is closed, so a value offered in its place is a schema violation refused before any byte reaches disk. Errors, journals, request receipts, transaction intents, unknown fields and observation caches cannot contain a value: none of them has a field for one, the value type cannot be encoded into any of them, and the no-value check runs on every body before the first byte of a transaction is written. A model transcript is the harness's own file, not Hive's, and a value cannot reach one from Hive because no Hive command prints, returns or exports a value and no launch passes one in a prompt, an argument or an environment. The transaction intent carries the whole body of every record, receipt and event the transaction will write and the outcome it will record, so the intent is the first place a record's bytes reach disk; the check therefore runs before the intent is written, the intent's own temporary file included, and so before any record's temporary file and not only before the final rename. Who runs it is fixed by the store as built: the store validates no record against its schema, and the owning package does, with the contract library's schema package, before it hands the transaction to the store's writer. The no-value check is part of that same validation, run by the owner on every body of the transaction through the schema package, and the store itself is unchanged by this contract. Publisher and model credentials are separate Spoors with separate purposes, and holding one cannot widen publishing authority or authority over a protected base: authority is read from its own record at the moment of action, as [Assimilation](#assimilation-on-the-mac) requires, and a Spoor is never that record.

Prove, in `test-dispatch`, that a Spoor round-trips with store, host, account identity and purpose and no field beyond those and what every record carries, that a request offering a literal marker `hive-marker-not-a-secret-0000` in place of any of those fields is `invalid` with nothing written and no file created under `tmp/` or `tx/`, and that a value-typed field in any record, receipt, intent, event or response body fails to encode with an error that does not contain the marker. Prove, in `test-contract`, that the value type's JSON and text encodings each fail with an error, that its print and debug forms are the one fixed redaction, that none of the four ever contains the marker, and that a transaction whose owner-side validation fails on any body leaves no intent, no temporary file and no record.

### How a value reaches exactly one command, and every way it must not

Retrieval happens inside the consuming process where possible: the consumer resolves the Spoor through Tendril at the moment of use, uses the value, and lets it go. Where a program takes a credential only through environment variables, Tendril retrieves into memory, builds a minimal environment holding that one variable beside the few the program needs to run, and executes the approved program with arguments that hold no secret. A value never travels through `env` on a command line, a populated environment written out, shell interpolation, a launch script that carries it, or a terminal daemon's memory: a program that needs a value is started by Tendril directly, never through tmux, and a session Hive starts inside tmux receives no value at all. A long-running process carries Spoors and resolves at each use; it never caches a value across uses.

A dependency that signs in by itself is a consumer that retrieves inside its own process, which this contract prefers, and Hive passes it nothing; this document says so for each of the six: Claude Code, Codex CLI and gh each sign in by themselves; Git reaches a remote under the credential helper its own configuration names; the no-mistakes daemon and the tmux server are long-running processes that receive no value from Hive, ever, and the sessions tmux starts and the steps the plugin runs sign in through the tools they run, under the same condition. Such a tool satisfies this contract only while its own login is kept in the platform's store. Hive's check for it is the tool's own report of whether it is signed in and of where its login is kept, run as the capability probe already is and never reading the content. A tool that reports a login kept in a file, or that cannot say where it is kept, makes the operation that needs it unavailable with the sanitized store condition of the next subsection, and the remedy is the user moving that login into the store with the tool's own command: Hive changes no tool's configuration and moves nothing itself. No Spoor stands for such a login. Tendril hands a value only to the one short-lived invocation that needs it: a program run under an identity that is not the operator's own login, such as the publication identity of [Synapse's publisher](#publication-github-as-an-optional-publisher) or the dispatch identity of the [GitHub integration](#claude-through-the-official-github-integration), and nothing else. Dispatch passes Spoors and scoped capabilities, never values: an Imperative for a Void session names the Spoors its work needs, by name and purpose, under allowed access, and the session resolves them in its own host's store, as the final consumer always does, local or remote. A credential reference is named on the Imperative of a dispatched item, which is a Hunt or a Prey that is a single Hunt, and never on a Target or on a Prey that holds Hunts, which have no Imperative. Nothing of Hive ships a value to the Void. Before the launch, the backend's `probe` asks the Void host, through the environment's supported surface, whether it holds an item for each named Spoor, and records present, absent or unknown and never a value; a Spoor the Void host does not hold, or whose presence cannot be read, is a hold with a named gap, not a launch.

Prove, in `test-contract`, that Tendril runs a recorded fake with exactly the declared environment variables, that the fake's recorded argument list and the Hive process's own environment never contain the marker, and that no Hive command, operation or response prints, returns or exports a value. Prove, in `test-dispatch`, that a launch of `claude` or `codex` passes no credential of any kind, that a Void launch's Imperative names each Spoor its work needs by name and purpose and never the marker, that the launch is held with a named gap when the recorded fake of the Void host reports one named Spoor absent or unreadable, and that no session is created for a held launch.

### Which store on which platform, and what happens when none is chosen, locked or missing

On macOS the default store is the keychain: with no recorded choice, a Spoor resolves in the keychain, and this revision designs no other macOS store. Hive reaches it by running the platform's own `security` program, Hive's first declared platform utility, through the one process-execution path with a fixed argument list and no shell. On Windows and Linux Hive asks the user which store to use: when an operation first needs a secret on a host whose home records no store, `dispatch` raises one Mind's word through `word`, once, naming the host and the stores Hive has an adapter for, and the answer is recorded in the home; the question is never a prompt of Hive's own, so nothing it asks can take a value. Until a store is recorded, every operation that needs a secret waits on that one hold. This revision designs no adapter for a store nobody has chosen: Hive is delivered for macOS, Linux is where it is built and tested, and Windows is not a delivered platform, so the Linux and Windows clause is the contract and the refusal, and an adapter for a chosen store is work that arrives with the choice. Each condition answers in the command contract's terms, with a sanitized error naming the Spoor, or for a tool's own login the tool, the store and the condition, and never the value; nothing falls back to another store, to a file or to a prompt of Hive's own. There is no general read-a-secret command: a value resolves only inside a named operation that declares the Spoor it uses.

| Condition | Status and code |
| --- | --- |
| No store recorded on this host | `held`, with `error.hold` naming the one Mind's word raised for it |
| Recorded store locked | `unavailable`, `secret_store_locked` |
| Item named by the Spoor missing from the store | `unavailable`, `secret_missing` |
| Platform utility absent | `unavailable`, `platform_utility_missing` |
| Platform utility present but unsupported | `unavailable`, `platform_utility_unusable` |
| Recorded store with no adapter in this build | `unavailable`, `secret_store_unsupported` |
| A tool that signs in by itself reports its login kept in a file, or cannot say where it is kept | `unavailable`, `secret_store_unsupported` |

Prove, with a recorded fake of `security` placed first on the search path, that a missing item, a locked keychain and an unsupported tool each refuse with `unavailable`, their code and an error carrying the Spoor's name and no marker, that the same operation on a Linux home with no recorded store is `held` on one hold before the fake is run and a second operation raises no second hold, and that a recorded store with no adapter is `unavailable` without running anything. Prove the same with a recorded fake of a tool that signs in by itself: one reporting its login kept in a file and one that cannot say where it is kept each make the operation that needs it `unavailable` with `secret_store_unsupported` and no marker, one reporting the platform's store runs it, and Hive passes the tool no value and changes none of its configuration. Real keychain behavior is proved only on a Mac, as [Implementation evidence still required](#implementation-evidence-still-required) lists.

### How a secret is enrolled, and what Hive checks

Hive never accepts a value itself. A secret is enrolled in the platform's own prompt, outside Hive, and the Hive Mind then tells Hive the Spoor: store, host, account identity and purpose. Hive records the Spoor and checks only that the secret is there: the presence check asks the store whether an item answering to the Spoor is present and retrieves no value, through the keychain adapter's presence operation, which asks for the item's attributes and never for its content; nothing is resolved and nothing is discarded. Enrolment in the UI is a separate secure path from ordinary messages, screenshots, reviews and attachments: the one [enrolment status surface](#ui) shows each Spoor's name, purpose and whether it resolves, and takes no value. A secret never enters an Imperative, a session message or a replay record: no operation that writes one has a field for a value, and the owner's no-value check runs on every body before the first byte is written. What that check recognizes is refused whole, never redacted, truncated or reflowed, which is the record rule that a writer that cannot keep a string whole refuses the write; what it cannot recognize is kept exactly, as the record contract requires, and is a found copy from the moment it is found, handled under the next subsection. Beyond a value-typed field, the check recognizes a short fixed list of credential shapes that are unmistakable by construction: a vendor's token prefix together with its fixed length and alphabet, and the armour line of a private key. The list lives in the contract library's schema package, each entry named, and it changes only as a contract change. A match is refused whole, `invalid` with code `secret_shape_recognized`, with nothing written, and the refusal names the field and the shape, never the text. Prose that merely mentions a prefix does not match, because a shape includes its whole length and alphabet. The list is a floor, not a claim to recognize every secret: what it does not recognize is kept exactly and is a found copy when found. Prove, in `test-contract`, that a request whose text carries a string of a listed shape is refused whole with nothing written, that the refusal names the field and the shape and not the text, and that a sentence that mentions a prefix without the full shape is accepted. Workers are model sessions with a shell running as the same user, and the contract holds against a worker that asks for a secret by name: no Hive command prints, returns or exports a value, the status surface shows names, purpose and resolution and never a value, and an Imperative's allowed access names Spoors, never values. What the platform's own access control grants a process running as the operator is the platform's boundary, not Hive's claim; Hive's claim is that nothing it builds widens it.

Prove, in `test-dispatch`, that enrolment records a Spoor and a presence receipt that holds no value, that the fake saw a request for attributes and none for content, that enrolment with a value offered in the request is `invalid` and writes nothing, and that the status projection for a Spoor whose item the fake does not hold reads unresolved and never carries the marker. Prove, in `test-ui`, that the enrolment surface renders name, purpose and resolution from that projection, has no field that accepts a value, and that a message or note containing the marker reaches no Spoor and no launch.

### What happens when a copy is found where none may be

A detected unauthorized copy of a value, in a record, a log, a transcript, a repository or anywhere a value may not be, raises one sanitized incident naming where the copy was found, the Spoor it belongs to where that is known, and the time, never the value, and then waits for the human's word. The incident is a Mind's word, raised through `hive-word hold` by the owning supervisor, the Hive or the Fleet whose home or project holds the copy, which is how every held question is raised; `dispatch` records the incident against the Spoor as a receipt, `dispatch.spoor.incident`, through `hive-fleet`, when the supervisor names one. Only a supervisor or the Hive Mind raises an incident, and on three grounds only: the Hive Mind's or a supervisor's instruction naming a place, or a package's own report of a found copy in a response. An external scanner's report is read as an ordinary instruction naming a place, with no authority of its own. Hive runs no scheduled scan for copies: the shape list at the writer is the floor, and detection after the fact is a person's or a package's report, never part of the writer's check. A package whose writer's check refuses a value, or whose reader finds one, writes nothing and reports the finding in its response, and the supervisor that receives the response raises the one hold; a worker that finds one reports it as a blocker receipt, and its supervisor raises the hold. Hive neither deletes, rewrites nor rotates anything by itself: migration to another store, rotation and deletion are separate authorized operations, each with its own authority and receipt, and an incident is not authority for any of them. Exact-text preservation stands: a record that already holds a found copy is not edited, and the remedy is rotation under the human's word.

Prove, in `test-dispatch`, that an incident raised for a record holding the marker yields a hold and a receipt whose text does not contain the marker, that the record is unchanged, that a second report of the same copy raises no second hold, and that no rotation, migration or deletion runs without a separate authorized request.

### Hive's command contract and a value

The [command contract](#repository-and-package-contracts) records requests for replay, writes intents before records, keeps text exactly and preserves unknown fields. None of the four can carry a value, and each has one check for the day one is offered:

| Rule of the command contract | Why a value cannot arrive there | The check when one does |
| --- | --- | --- |
| Requests are recorded for replay | A value is never an input to a Hive command: no operation's request schema has a field for one, and requests are closed. | A request with a value in place of a Spoor field is `invalid` on schema validation, which runs before anything is read or written, so no replay record and no temporary file exists. |
| Intents are written before records | An intent carries the whole body of every record, receipt and event the transaction will write and the outcome it will record, so it is the first place a record's bytes reach disk; a value Hive resolved cannot be among them, because the value type cannot be encoded. | The owner's no-value check runs on every body of the transaction before the intent is written, so a recognized value is refused before the intent's temporary file exists and therefore before any record's. |
| Text is kept exactly | A value Hive resolved cannot become text, because the value type's text encoding fails. Text from outside is never an input that names a value: no schema has a field for one. | The owner's check runs before the first byte. What it recognizes is refused whole, never redacted, truncated or reflowed, as the rule that a writer that cannot keep a string whole refuses the write already requires; what it cannot recognize is kept exactly and is a found copy from the moment it is found, under the incident above. |
| Unknown fields are preserved | The `unknown` member carries what a migration did not recognize; Hive never writes a resolved value, so it cannot land there. | A migration runs the same owner's check over `unknown` before its first byte: a recognized value refuses the migration of that record whole, with nothing written, and an unrecognized string is kept exactly and is a found copy when found. |

### No store of Hive's own

Hive references the platform's store and fetches at run time into the one command that needs the value; it builds natively only what sits around the store: the Spoor, Tendril, the keychain adapter over `security`, the enrolment check, the status surface and the incident. That choice gives up five things, stated here once and plainly. Moving to a new Mac means enrolling each secret again there, because Hive holds nothing to move. Hive carries no export, backup or sync of values. Hive has no screen that lists, shows or edits values; it can show names, purpose and whether each one resolves. On Linux nothing that needs a secret works until its user has named a store and Hive has an adapter for it. On a platform where a tool offers no store-backed login, nothing that needs that tool runs.

### Why a platform utility is not a seventh dependency

The six core dependencies are programs Hive finds on the search path and that someone must install; [Tooling](#tooling) counts them because each is a prerequisite a delivery can lack. A platform utility is part of the platform substrate, as the inventory already says of macOS and system utilities: it is present wherever the platform is, installed by nobody and upgraded with the operating system, and Hive's package declarations carry a `platform` list precisely so that a utility can be named with its reason and seen by the distribution proof. `security` therefore enters that list, for the packages that run Tendril against the keychain, and the six dependencies and the seven packages stay exactly as they are. No third-party library and no C toolchain is used to reach the keychain: the utility is run, through the one process-execution path, like any other program. The hermetic test targets prove the contract against a recorded fake of `security`, as they do for the six; real keychain behavior is a Mac-only qualification with a made-up marker value, listed under [Implementation evidence still required](#implementation-evidence-still-required), because a Linux run cannot establish it.

### Where the parts enter the plan

The [ordered implementation plan](#ordered-implementation-plan) keeps its order and its ownership. The Spoor record, its enrolment check and its status projection enter with `dispatch` in stage 4, where the Fleet's adapter configuration first records a credential reference. Tendril and the keychain adapter over `security` enter the contract library in the same stage, with the first consumer that must hand a value over; `synapse` adds its publisher's Spoor and a call to `dispatch` for the lookup in stage 5, and `ui` adds the enrolment status surface in stage 6. Two calls between packages enter with these parts: `dispatch` to `word`, in stage 4, for the one Mind's word that asks which store a host uses, and `synapse` to `dispatch`, in stage 5, for the Spoor lookup; both are declared in that contract change and first used by the stage that adds them, and the call graph stays free of cycles, since `word` calls only `pool`, `pool` calls nothing, and `dispatch` calls neither `synapse` nor `shadow` nor `ui`. The no-value check enters in two steps, the second adding to the first and reopening nothing: from stage 2's first writer it is the owner's validation against closed schemas that have no field for a value together with the fixed list of credential shapes in the contract library's schema package, which enters there with that writer because the Pool is the first package to keep free text; the value type joins it when Tendril enters in stage 4, so that a resolved value cannot be encoded. A change to the shape list is a contract change and changes no schema. The `spoor_` identifier prefix is registered with the first record that names a Spoor, stage 2's Imperative, while the Spoor record itself enters in stage 4, so stage 2's schema is not reopened to add it. Earlier stages leave room, and the amendments this section needed of the accepted contracts were made as one minor contract change, which changed no landed record and no built behaviour: stage 1's one process-execution path is where Tendril sits, its closed schemas are what refuse a value, its `platform` declaration list is where `security` is named, and its rule that the owner validates every body with the schema package before the store writes the intent is where the no-value check runs, so the store as built changes nothing and the check is an addition to the schema package's validation; stage 2's Imperative schema names Spoors under allowed access and has no field for a value; stage 3's leases and checkout hooks carry no credential and name none.

## Imperatives are given at dispatch

### Admission checks the Imperative

Object, Standard, Output and Boundary are required typed fields inside the Imperative's own sections, in the single schema defined under [render and deliver](#render-and-deliver-the-imperative).
There is no separate four-part block beside the Imperative and no independently maintained admission copy of its contents.
`hive-admit` preserves the original request, checks that schema and records a receipt bound to its revision/digest and the authority used.
Fields may draw on an identified, readable, revision-bound task/specification record.

When every part can be filled with high confidence from the command's words and the record, state that reading in the dispatch and proceed within existing authority, without a separate restatement-and-wait turn.
Stop to ask when a part is a genuine guess that would change what gets built, or when a boundary involving spend, deletion, security or publication needs the Hive Mind's authority.
Already explicit, applicable authority satisfies that boundary check; inference cannot supply it. A question from the Hive Mind is not authorization, and a deferral is never approval.
Record the unresolved part and its consequence as a hold; the Fleet resolves technical detail already inside accepted scope.
Dispatch without all four fields is refused on every launch path, even when the intended work seems obvious.
Malformed input likewise fails closed.
An Imperative names the access its work needs as Spoors and has no field for a credential value; one offered in any field is refused before anything is written, under [Secrets](#secrets-hive-keeps-none).

Record-only maintenance may use a narrower schema only when a named, configured exemption proves it cannot launch project work or broaden authority. Provisioning a persistent Fleet uses a charter/provisioning record instead of pretending it is a Swarm task. Neither exemption allows build work to bypass admission. Hooks may improve feedback, but `hive-dispatch` and every adapter entry point enforce the same native check for local and Void work.

The validated Imperative schema renders both the dispatch text and launch parameters, with admission/specification revisions and policy digest embedded in the private receipt.
Contradictory includes or independently inferred flags refuse dispatch.
Steering that changes scope revises that same schema and repeats the affected checks; it cannot smuggle a new permission through a message.

| Independent dispatch axis | Contract |
| --- | --- |
| Placement | Where this Hunt runs: on the Mac or in a qualified Void backend, with exact runtime/isolation ownership. The choice is made for the Hunt, by the Hive Mind's instruction, the Pool item's requested place or the resolved policy, recorded on the item and rendered into the Imperative's Setup from the Pool stage; a local-only project admits only the Mac, a Void placement needs a pushed source branch, and a parked backend is refused, never substituted. Where Synapse validation is selected, every place delivers to the same Synapse on the Mac. |
| Validation | Required Synapse executor and proof policy, or an explicitly authorized direct-delivery policy. A change of publication mode cannot remove a required gate. |
| Publication | Harvest or local-only branch delivery. A local-only route needs no forge binding, remote or fabricated Harvest. |
| Assimilation authority | Attended explicit word or recorded autonomous posture, checked separately at landing. Neither validation nor publication supplies it. |

Validated local-only delivery is a first-class combination: the Fleet validates and presents the exact local branch; the Hive retains local landing authority. The inherited command-mode inputs are compatibility syntax, not the internal state model.

### Render and deliver the Imperative

The Hive owns the canonical Imperative in its private home, or delegates custody to the dispatching Fleet's private home with a parent reference. Nothing requires committing it to a public repository. The source branch must be pushed for a Void launch; the Imperative is supplied as the session launch prompt or rendered for the selected GitHub integration under the visibility rules below. Provider receipt of that prompt does not authorize publishing it in a Harvest, comment, log, or code file.

Preserve the four sections from firstmate's [dispatch scaffold](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/bin/fm-brief.sh), with the command fields embedded as follows:

1. **Task:** contains **Object** (project, task and concrete artifact or behavior) and **Standard** (acceptance conditions, required evidence and authoritative requirements/rules). Preserve the Hive Mind's intent separately from the Fleet's implementation specification, include the substance of referenced evidence and assign the dispatch class. Do not turn implementation choices into purported operator intent.
2. **Setup:** binds that Object to repository, immutable source SHA/base, output branch rule, role, harness/placement, dependencies, available tools, allowed access, named as Spoors under [Secrets](#secrets-hive-keeps-none), and isolation assertions. Local execution verifies physical working directory and repository top level before branching; Void execution verifies repository/base/source identity before editing. Setup implements the same schema's Boundary and cannot expand it.
3. **Rules:** contains **Boundary** (scope, exclusions, allowed effects, resources, permissions and stop/escalation conditions), including authorized repair scope and finite retry limits. Supply complete validation commands that implement the Standard and identify the delivery/decision channels and blocker owner. Do not assume private Mac files or local tools exist in the Void.
4. **Definition of done:** contains **Output** (exact deliverable, recipient, validation/publication choices and completion evidence against the Standard). A validated Harvest requires agreed Synapse results at its current head; a direct Harvest requires publication and its stated checks; validated local-only work requires a clean branch plus passing current-head Synapse evidence; an explicitly authorized direct local route carries its stated checks; a Lictor requires a collected report and decision inventory. Define the worker's stopping point separately from later Assimilation.

An Imperative for a clear build is minimal; a plain copy or upload of an existing artifact is done directly by the supervisor and dispatches no Swarm. Every Imperative pre-rules the three routine stops, so that the supervisor rules only on what is new: a named consumer file outside the grant, a document the change falsified, and a documentation-only finding after the gate. A Hunt that owes a capture, a proof or a special run is dispatched only with that step's exact procedure written in its Rules, and its worker stops at the first uncovered obstacle.

The rendered prompt starts with the worker role boundary, so project instructions cannot turn a Swarm into a supervisor. Before launch, validate that the text fits the selected transport without truncation and that required files, network access, result collection, tool installation, and credentials are already available. A credential value never belongs in the prompt: the Imperative names the Spoors the work needs, by name and purpose, under allowed access, the consumer resolves each in its own host's store, and for a Void session the backend's `probe` establishes before the launch that the host holds each named one, else the launch is held with a named gap, under [Secrets](#secrets-hive-keeps-none); unrelated private history never belongs in the prompt either. If those requirements cannot be met, hold dispatch or choose an explicitly permitted local route.

The Claude session adapter passes the rendered text to `claude --cloud "<imperative-text>"`; the measured Codex legacy command is `codex cloud exec --env <environment-id> --branch <branch> --attempts 1 "<imperative-text>"`, retained as evidence while dispatch is parked. The new Codex backend must supply a supported command-line route once verified; it must not reuse legacy IDs by assumption. A routine-based dispatch may carry the text in its supported trigger payload. These are argument shapes, not instructions to interpolate arbitrary text into shell code. Launchers pass an argument vector or supported input channel, pass no credential, and keep prompt-bearing transcripts private; the harness signs in by itself and Hive passes it nothing, and it runs only while its login is kept in the platform's store, under [Secrets](#secrets-hive-keeps-none).

For GitHub-triggered work, the canonical Imperative still stays private. The Fleet may render a separately authorized, complete public-safe execution prompt whose scope, checks and stop conditions are sufficient without private context. A public `@claude` comment, workflow input, log or artifact cannot transport the canonical copy. If the task cannot be fully specified through the selected transport without exposing private material, dispatch it through a verified private session route or locally instead. No confidential prompt relies on log masking as its privacy boundary.

A Swarm never waits in the Void for its next assignment, a missing dependency, review approval, or Assimilation. It completes its Imperative, pushes its authorized result, records a receipt, and stops. A Lictor likewise returns its report and stops. Later fixes are bounded new work, possibly resumed through a vendor event. An unexpected decision produces a blocker receipt and an exit, not an idle polling session.

Steering changes the canonical Imperative first. The Fleet saves a revision, assigns a message ID, and records transport acceptance separately from worker acknowledgment. Claude cloud sessions can accept a steer by session ID while active; an Actions run does not inherit that control. A Codex Cloud task is submit-and-collect; no cloud steer command was established. Changed Codex work becomes a successor Imperative after reconciliation of the existing task, rather than a guessed follow-up API. A late steer cannot silently invalidate a finished deliverable without creating a new delivery obligation.

The measured Claude exercise used a committed brief. Prompt delivery is supported by the CLI, but the intended **prompt-only bootstrap and private canonical-copy contract still need an integration check**. The implementation must not copy that exercise's committed-brief technique into Hive by accident.

## Eight dispatch classes

The class numbers stay **0–7**. They classify the work, independently of whether its deliverable is a Swarm change or a Lictor report.

| Class | Scope |
| --- | --- |
| 0 — Option weighing and feasibility | Compare plausible approaches, establish feasibility, and recommend a direction before the Hive Mind chooses. Produce evidence and tradeoffs, not speculative implementation. |
| 1 — Architecture and specification | Define boundaries, behavior, interfaces, invariants, and a buildable specification. Carry consequential design reasoning into implementation where that reasoning still determines the work. |
| 2 — Adversarial review | Challenge a proposed design or change for correctness, missing requirements, regressions, and failure cases. Findings are a review deliverable; they do not confer permission to implement or Assimilate. |
| 3 — Partially specified build | Implement an agreed outcome whose behavior or scenarios are known but whose internal structure still needs substantial definition. Preserve the reasoning requirements of an architectural change rather than treating a written outline as a mechanical recipe. |
| 4 — Specified build | Implement a bounded feature or fix whose behavior, approach, and acceptance conditions are sufficiently settled. Remaining uncertainty is ordinary implementation detail, not an unresolved product or architecture choice. |
| 5 — Structured research | Gather and organize existing evidence: inventories, interface maps, source comparisons, reproducible captures, and evidence tables. Escalate to the relevant reasoning class if the work turns into feasibility, architecture, or diagnosis. |
| 6 — Diagnosis | Reproduce a failure, distinguish competing causes, and establish a supported explanation and repair direction. An investigation request alone does not authorize shipping that repair. |
| 7 — Mechanical work | Perform narrow, readily checked edits such as a specified rename, typo correction, or deterministic formatting change. Hidden behavioral decisions require reclassification. |

The private dispatch configuration maps each class to eligible Claude/Codex profiles and placement preferences, resolved through Hive, workspace and project scope. Each profile includes harness, real model name, effort, supported capabilities, and selection rationale. Separate entries configure the Hive, Fleet supervision, Synapse reviewers, validation steps, and fixers; those roles do not create extra dispatch classes.

The Fleet resolves the class and concrete profile at every intake. An explicit task instruction wins, followed by the configured matching rule, configured default, then the supported static default. Inspect actual model support and available usage evidence; record uncertainty rather than inventing precision. A malformed configuration, unsupported required capability, or unusable authentication stops dispatch; an unusable authentication is a Spoor that does not resolve, reported without its value under [Secrets](#secrets-hive-keeps-none). Never silently change vendor, model, permission mode, or placement to bypass a refusal. Where local fallback is preauthorized, record the fallback and its reason in the execution record.

### Effective policy and resource admission

`hive-policy resolve` applies the effective scoped rules to every role: the Hive, Fleet supervisors, eight dispatch classes, reviewers, fixers and validation steps. It emits a receipt with requested and resolved model/effort, harness, placement, permissions, validation/publication choices, resource reservation, allowed fallback and the source/rule revisions that selected them. Restart uses this same resolver, not a separate default profile. An explicit request retains its priority within current authority; conflicts or unavailable capabilities return a hold rather than a silent downgrade.

The Swarm's dispatch-matrix editor is one bounded policy write. It sends a policy request to the Hive's policy owner through `dispatch` and never writes private configuration directly. The request binds its authenticated origin, request/replay ID, target Hive, workspace or project scope, expected policy revision and effective-rule digest, exact patch and authority reference. The owner validates supported values, current authority and inheritance, then compares revisions atomically at application. Accepted, Applied and rejected or conflict receipts are separate. An explicit task instruction keeps its priority, inherited defaults are shown rather than copied into each child scope, and neither a parent update nor a concurrent editor can silently overwrite newer policy. An applied change affects later resolutions; running generations keep the receipt they were dispatched with. A request that names an expiry or a lift condition is applied as a temporary rule in the rule store under [Scheduled](#scheduled), and the resolver honours its expiry whether or not a later receipt records it. A change to a product, spend or authority rule that needs the Hive Mind goes through `word`; an ordinary, already authorized setting gains no second approval step.

Resource readers provide timestamped, attributed evidence with an accuracy/freshness classification. Configured policy decides which usage/credit/resource readings are required and how to weigh available capacity. Unknown or stale values cannot prove capacity; missing required evidence blocks admission, while optional metering can remain visibly unknown. Threshold values, comparison operators, scope, Hunt limits, expiry and credit authority are configuration. No Hunt limit binds unless the Hive Mind states one; a stated limit is a temporary rule with its expiry, and no earlier limit returns as a default. A floor policy defined as at-or-below must fire at equality; it is not a strictly-below check and cannot retain a superseded single-role exception.

Record configured local resource reservations atomically with launch intent and reconcile uncertain submissions before releasing them; a provider allowance observation is evidence, not a reservation with the vendor. `hive-park` waits for a safe checkpoint or pipeline gate, records custody, outstanding work, the resource blocker and resume authority, and stops admitting dependent work. It does not abort a validation round to save capacity. `hive-resume` rechecks fresh evidence, current policy and authority and continues the owned task/gate once, without changing accounts, funding, credentials or model to escape the hold; a credential it needs is the same Spoor, resolved again at the resume, under [Secrets](#secrets-hive-keeps-none). A timer or resource recovery is not itself new spend authority.

## Runtime adapters: what the Void adds

Each adapter implements `probe`, `launch`, `observe`, `collect`, and a capability declaration for `steer`, `interrupt`, `resume`, and `stop`. These are Hive interfaces, not assumed vendor commands. Results distinguish accepted, running, finished, failed, unknown, and unsupported; they carry source evidence and the bound task generation. Completion always requires collection and delivery checks above the adapter.

Private dispatch configuration names the backend explicitly: `claude-local`, `claude-session`, `claude-github`, `codex-local`, `codex-legacy`, or `codex-new`. These are proposed Hive identifiers. A capability record stores implementation version, environment generation, authentication context reference, which names the harness and the account it reports and is neither a Spoor nor a value, checked only by the harness's own report of whether it is signed in and of where its login is kept, under [Secrets](#secrets-hive-keeps-none), supported operations, result/retention contract, evidence receipts, last probe, next recheck and retirement state. Readiness is per capability: accepted task creation alone cannot enable publication or Astra reviews. The Fleet chooses only a backend meeting the Imperative's requirements and records any preauthorized fallback. Every backend runs on the operator's subscription through its harness, on the Mac and in the Void alike; Hive holds no API key and dispatches through none.

The shared contract owns source identity, private Imperatives, result schema, Synapse and Assimilation. Vendor-specific environment discovery and commands stay inside their backend. A parked, missing or retired capability raises one actionable blocker and holds dependent work; it does not cause repeated launches or an automatic migration of a running task.

Where a Hunt runs is a choice made for that Hunt, and Hive is the proof of concept of the hybrid: the same Pool item, Imperative, admission and, where validation is selected, Synapse serve a Swarm on the Mac and a Swarm in a Claude cloud session, with Codex Cloud named as a later place and parked until its own readiness contract passes. The choice is recorded on the Pool item from the Pool stage, resolved and bound by `dispatch` from the session stage, and proved end to end in the last stage, as the [ordered implementation plan](#ordered-implementation-plan) states. The Void adds a place to run and nothing else: a result built there is collected to the Mac, where Synapse validates it like any other where validation is selected, and a direct Harvest goes on to publication and its stated checks; no gate step or reviewer runs in the Void, and a repair dispatched there is a Hunt like any other, under the ledger's one-writer rule.

### Local Claude and Codex

The local adapter ports firstmate's runtime/harness separation. `hive-dispatch` acquires an isolated worktree from its configured provider, records ownership, launches `claude` or `codex` with the resolved profile through the verified terminal backend, and supplies the private Imperative. It records the runtime endpoint, worktree, branch and session identity before accepting worker status. It passes no credential: Claude Code and Codex CLI sign in by themselves and Hive passes them nothing, each launches only while its login is kept in the platform's store, and a session started inside tmux receives no value, under [Secrets](#secrets-hive-keeps-none).

Two launch rules apply to every session Hive starts on the Mac, whether a Swarm, Lictor, Fleet or review session. First, the harness's self-update is disabled for the launched session: the execution record binds an implementation version and capability-evidence revision that running work depends on, and a harness updating itself mid-fleet can leave the shared install unusable for every other session, so updating the harness remains a separate guarded operation and never a side effect of a launch. Second, the session starts directly on the Imperative with per-launch flags and a Hive-owned per-launch settings file: vendor startup prompts are pre-answered for that launch, browser integration is off unless the Imperative selects a browser task, and no launch writes the operator's global harness settings or a Fleet home's own. Each flag is passed only after a probe of the installed CLI confirms it is supported; an unsupported flag holds the launch with a named capability gap rather than falling back to a global write or an interactive prompt. Prove that a session launched while a newer harness release is available keeps its recorded implementation version until it exits and leaves the shared install's binary unchanged, that a stock launch with a browser extension installed reaches its first Imperative turn without an interactive prompt while the operator's global settings are identical before and after, and that the same launch on a CLI lacking the flag holds instead of starting. Sources: [kunchenguid/firstmate#7041](https://github.com/kunchenguid/firstmate/issues/7041) and [kunchenguid/firstmate#7042](https://github.com/kunchenguid/firstmate/issues/7042).

`hive-send` writes a durable steering message and rings the recorded endpoint. `hive-control` performs verified lifecycle operations; relaunch preserves the same worktree and work. `hive-state` reconciles the selected Synapse run, semantic harness activity, inbox acknowledgment and status journal. It does not infer a live run from a stale status tail. Project-specific execution and capacity controls remain in the project's test configuration.

No worker may administer a shared pipeline daemon or another task's worktree. A missing endpoint is not proof that work was lost or that a second endpoint is safe. A pipeline client timeout first prompts inspection and reattachment; a confirmed daemon failure is a supervisor-owned blocker. Preserve Codex compaction and Claude handover/recovery behavior through their respective harness adapters rather than imposing one vendor's lifecycle on the other.

### Fleets with local-only custody

`hive-fleet provision` creates or selects the workspace's Fleet and registers a local-only project under it without inventing a forge binding. A Fleet is created only on the Hive Mind's word, and a retired Fleet is reseeded from its archive, never deleted. A local-only project admits only the Mac as a place: a Void placement needs a pushed source branch, and so a forge binding, which the project does not have. The workspace charter records the owning supervisor and parent and, for each project, its project/clone identity, validation policy, publication mode and authority references; a local-only registration keeps the Hive's landing authority. `route` names the workspace and project, sends the work to that Fleet's Pool and preserves one parent handoff receipt. The Fleet owns definition acceptance, isolated branches, Swarm supervision, validation and evidence collection for its registered projects, which can mix local-only and Harvest delivery; the Hive performs authorized local Assimilation.

Isolation ownership binds the private home, workspace, project and clone, provider, task generation and branch/worktree. Two clones of the same origin must not collide in one Spawning Pool. Recovery reconciles those identities and provider receipts rather than guessing from a branch name or an apparently free slot. Provisioning, routing, restart and cleanup must work through the same native interfaces for local-only and Harvest projects; manual symlink/configuration wiring is not an accepted fallback.

Workspace, Fleet home, project and clone have separate stable identities. Provisioning is idempotent on the workspace identity; each project registration keeps its own validation and publication defaults and authority. A Hive operational task may be explicitly projectless, but project work never inherits an arbitrarily selected project. Reassigning a project to another workspace is refused while its work is in flight, or runs as a separately guarded migration that preserves the original task generations, endpoints, branch custody, decisions and historical receipts; changing a label re-homes none of them, and no project-move UI is required. A Fleet stow or restart targets the workspace supervisor's exact session generation and shows that scope in its operation receipt; a selected Subsector does not narrow it to one project. Child work keeps its own independent state and authority.

On completion, the Fleet presents the clean exact branch and its validation receipt to the Hive. Failed validation, unknown branch custody, unresolved decisions or unavailable proof keeps the handoff pending. Cleanup remains with the recorded owner and requires safe reachability of the work and retained decisions; a local-only project is not exempt from preservation or validation.

### Claude in the Void

**Measured on 2026-10-10:** a launch from a pushed branch was accepted in about 14.5 seconds; a steer was accepted in about 1.3 seconds and its pushed acknowledgment became visible on the Mac within 43 seconds. The same session opened a Harvest through GitHub REST, the vendor's Auto-fix repaired both a failed check and a review comment, all three native OS checks of that repository's own workflow passed, and Assimilation occurred on the Mac. This establishes a small end-to-end delivery path and the session's reach into GitHub, not desktop-platform parity and not Hive's Synapse, which runs on the Mac; the check, review and repair steps it exercised on GitHub are evidence about the vendor, not steps of the gate.

The implementation sequence is:

1. Persist the launch attempt, expected repository/branch/source and prompt digest. Run `claude --cloud "<imperative-text>"` with an interactive terminal attached: the measured launch refused piped stdout. Capture the returned session ID and URL privately without treating CLI exit as task completion.
2. Bind the session's actual output branch after validating its receipt against the launch record. Claude may choose a branch name different from the source branch; never adopt an arbitrary new branch solely because it appeared recently.
3. For steering, run `claude -p "<revision-text>" --cloud <session-id> --output-format json`. An `ok` response proves queue acceptance. Require a matching message acknowledgment or observed result before calling the steer applied.
4. Collect the pushed head and sanitized delivery receipt: fetch the bound output branch into a Mac-owned collection worktree from the Spawning Pool, verify repository, base and head against the launch record, and record the collection receipt. Where the Imperative's validation axis selects Synapse, it then runs there, on the Mac, exactly as for a head built locally; a direct Harvest needs no gate and goes on to publication and its stated checks. Where the publication axis selects a Harvest and authorizes the Swarm to open it, the Swarm creates it through repository-scoped REST with the selected gh adapter, `gh api --method POST repos/<repository>/pulls --input <payload-file>`, after checking for an existing Harvest for that branch; where none exists, the Mac's publisher opens it, and otherwise adopts the one it finds for that branch. The measured cloud proxy rejected GraphQL-dependent creation and accepted REST; the plain-gh transport is qualified in the selected environment before the Void uses it.
5. Finish the assignment and stop. A finding Synapse raises against the collected head becomes a bounded repair Imperative that the Fleet dispatches to the place chosen for it, on the Mac or in a new cloud session, under the ledger's one fix writer; no vendor subscription on the Harvest writes to the branch.

The measurement does **not** establish a headless native session-status command. `observe` must use a supported session-state surface when one is available and otherwise return native state as unknown, while separately reading authenticated GitHub progress. Do not invent `claude cloud status`, scrape undocumented endpoints, or send model messages merely to ask whether a session is alive. Optional `claude --teleport <session-id>` is a recovery/inspection path; it is not Assimilation.

The measurement did not establish the selected plain-gh adapter's readiness, and redirected Actions logs were inaccessible through the remote proxy. Environment preparation must verify gh availability, complete REST responses and result collection before dispatch, and, through the backend's `probe`, that the Void host holds an item for each Spoor the Imperative names under allowed access: Hive ships no value, the session resolves each Spoor in its own host's store, and a Spoor the host does not hold is a hold with a named gap, not a launch, under [Secrets](#secrets-hive-keeps-none). The gate's own logs are on the Mac; where a repair Imperative for a cloud session needs output that the Void cannot read, such as a project's own hosted check, the Mac obtains and sanitizes the relevant output into that Imperative. Committed repository instructions can travel with the source, but private Mac settings and installed plugins must not be assumed to travel. [Claude cloud documentation](https://code.claude.com/docs/en/claude-code-on-the-web) describes the supported launch and recovery surface.

### Claude through the official GitHub integration

The second Claude execution transport is [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions). It runs Claude on a GitHub Actions runner: an `@claude` mention invokes interactive work, while a workflow's `prompt` input supports event-driven automation. It is separate from a Claude cloud session, even where the same GitHub App is involved, and it is a place where a Hunt may run, never a step of Synapse: its pushed head is collected on the Mac like any other Void result and, where Synapse validation is selected, validated there, and it holds no review role. This transport is documented but was not exercised by the cloud-session measurement.

A Fleet's private adapter configuration records, for each registered project using this transport, the installed integration, pinned Action revision, workflow identity, permitted trigger actors, credential reference, public prompt policy, model profile, turn/time limits, output schema and result retention. The credential reference is a Spoor under [Secrets](#secrets-hive-keeps-none): the dispatch identity's token is resolved through the launch primitive into the one `gh` invocation that triggers a run and is never written into this configuration, and the workflow's own credentials live in the forge's store, where the Action resolves them. Provisioning the App, credentials and workflow is separate authorized setup; the adapter refuses launch until those prerequisites and publication permissions have been verified.

For a public-safe request, `launch` uses the configured trigger, for example `gh api --method POST repos/<repository>/issues/<issue-or-harvest-number>/comments --input <payload-file>` with an authorized `@claude` request. Persist the request digest and correlation token first, then the comment receipt, matching Actions run and attempt. A successful comment post is not proof that a workflow started; bot-originated triggers must be exercised with the actual dispatch identity. Reconcile a timed-out post before retrying. No matching run within the configured launch deadline produces a blocker.

The workflow passes a complete rendered execution prompt to the pinned `anthropics/claude-code-action`, checks out and verifies the source identity, and uses the configured tool and model permissions. `observe` reads `actions/runs/<run-id>` and its `jobs` endpoint through `gh api`; `collect` validates the returned branch, head, Harvest and public-safe result against that run and task generation. The run's success alone cannot substitute for the delivery receipt or reviewer verdict. Private reports require another verified private collection route.

Additional comments are distinct bounded requests, not a promised steer of an in-flight run. The adapter advertises cancellation or rerun only after its ownership and semantics are verified. A failed or cancelled run preserves its branch and evidence for reconciliation. An Action-based repair and the gate's fix writer must never own the same branch simultaneously. A workflow that pushes has not completed delivery until the Mac has collected its head; a project's own workflows that run on that push are the project's evidence, not the gate.

Version-matched inspection of the [cloud command implementation](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/cloud-tasks/src/lib.rs), [environment resolution](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/cloud-tasks/src/env_detect.rs), and [submission client](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/cloud-tasks-client/src/http.rs) explains both legacy constraints: the submission payload carries no model-selection field, and the CLI's headless `status`, `list`, `diff` and `apply` commands do not export the final natural-language answer. The follow-up closes the retrieval gap through a separate internal reader, not a newly supported CLI export. Model selection remains unavailable on this path, so a generic `-c model=...` setting or an Astra request in the prompt cannot establish an Astra result.

The legacy result reader keeps its observed request shape, client version, authentication-context reference, which names the CLI and the account it reports and is neither a Spoor nor a value, under [Secrets](#secrets-hive-keeps-none), response schema and validation evidence privately. It issues only the read-only task-details call for a bound task using the same login, then validates task identity, terminal state, selected attempt, repository/source binding and complete final-message content; bind any model metadata as observed evidence and never fill it from the prompt. A missing field, ambiguous attempt, truncation, identity mismatch, authentication refusal or changed schema makes collection unknown or blocked. Preserve the raw response privately for diagnosis and revalidate after client or service changes. This is an internal, undocumented interface with compatibility risk; no stable public-API guarantee is claimed, and its identifiers or request shape must not be carried into the new backend by assumption.

For a route returning a diff, the Void Swarm makes its result durably collectable and stops; the local collection Swarm fulfills the push obligation. Record separate execution generations under the same delivery task. Verify retention and collect before its deadline. A backend that publishes directly supplies a verified branch instead. Both paths require the same source and result checks.

The inspected legacy task mapping is pending/ready/applied/error; failed and cancelled map to error, while unknown upstream states mapped to pending. Hive retains raw state evidence and treats an absent task, unreadable response, incomplete pagination or unrecognized state as unknown. Ready means available for collection, not passing Synapse. The [CLI reference](https://developers.openai.com/codex/cli/reference/) documents the experimental commands; compatibility must be measured per backend and release.

#### Enabling and retiring a Codex backend

Re-enable a Codex Cloud backend only after a supported command-line route demonstrates effective model selection and a controlled replay proves discovery, prompt-only dispatch, source binding, terminal success/failure observation, complete result collection, restart recovery and duplicate-submission prevention, followed by a Swarm change passing Synapse on the Mac through Mac Assimilation. Record the evidence and authorized configuration change; an accepted default-model task cannot release the parked state. Astra is not part of that re-enablement: the reviewers of Synapse run on the Mac, so Astra stays on local Codex, where model selection is honored and the selected model is verified there. A review-only task in the Void that returns complete findings and an explicit no-findings result at a known head is evidence about the backend, not a review the gate accepts, and a differently modeled cloud review is not accepted merely because its final text is collectable.

Run a Codex compatibility probe only when the Hive Mind explicitly authorizes it, in an authorized test context through ordinary admission, with no browser interaction. Store the tested version, official route, environment generation, task receipts, capability results and next action privately. A failed probe preserves the working backend configuration and records the concrete gap.

Record any announced retirement deadline and a dispatch cutoff that leaves time to collect active work. At that cutoff mark the backend draining and stop new dispatch; on lost access mark it unavailable immediately. A general deprecation notice does not itself prove that a still-working legacy route has stopped. Collect in-flight results while access remains, preserving branch, patch and review evidence outside provider retention. Do not translate legacy IDs into new IDs or move an uncertain running task by relaunching it. Reconcile each task, then issue a successor Imperative on a ready backend when the recorded authority permits. If results cannot be retrieved, record the loss or uncertainty and hold the task for recovery.

Switch to `codex-new` only after model selection and its own command-line readiness replay pass and dispatch is explicitly re-enabled; rollback selects another proved backend for new work without discarding old receipts. If legacy access ends first, Claude carries permitted Void work and Codex runs locally. An Imperative requiring Codex, Astra, a particular model or Void-only placement cannot silently become a different executor: use a preauthorized compatible fallback or return the choice to the Fleet. Retirement changes execution routing; it does not weaken either reviewer, Synapse evidence or Mac Assimilation authority.

## The Shadow

The Shadow is a lightweight Mac process, one owner per private home. It performs bounded reads without model calls, persists observations, and wakes a supervisor only for actionable changes. Claude's existing Stop-hook supervision ownership and Codex's existing checkpoint protocol remain available. The Hive observes its Fleets' routed summaries; each Fleet observes its own children. A Fleet's summary to its parent declares the owning home and workspace, the applicable project, its registered source membership, revision, cursor, coverage and freshness. Per-source cursors or a parent-assigned projection sequence order it; independent home journals are never treated as one global order. A cursor gap is recovered from a bound snapshot and the changes after it. The Hive-wide Mind's word and health projections carry the known records plus explicit incomplete coverage when a child's summary is missing or stale; a filtered map can neither hide a call nor imply all-clear. An answer routes to its original home, task and question revision through `word`. No process sweeps another home's endpoint namespace.

The cadence below is a configurable starting contract. Local timings retain upstream defaults; the faster remote timings are proposed Hive defaults, not measured service guarantees.

Bound each network read to 30 seconds, add modest jitter, use conditional requests where supported, and honor rate-limit retry times. Repeated transient failures back off from 60 to 300 seconds and then at most 900 seconds. An authentication refusal raises one actionable blocker naming the Spoor and never a value, under [Secrets](#secrets-hive-keeps-none); network loss raises one degraded-observation event and preserves the last observation with its timestamp. Staleness is visible and never used as a current green result. One slow repository must not block other due polls.

For local work, retain the distinction between a working-but-quiet interval, a declared wait, and a real blocker. The inherited working-stall inspection threshold is 240 seconds; a continuously busy turn has a separate one-hour inspection bound. Neither authorizes automatic termination. A declared wait names its dependency and clearing condition and is rechecked by its stated time or within four hours, whichever is sooner. The Hive Mind's held decisions do not repeatedly wake an away session; supervisor-owned decisions still receive attention. A cloud session does not remain allocated just to satisfy this wait mechanism.

The Hive supervises each Fleet session it launched with the same semantic busy/liveness source it arms for a Swarm: the launch wires the hooks that feed it through a Hive-owned per-launch settings file that reports into the Hive's own home, never through the Fleet home's own settings, so a Fleet mid-turn reads busy rather than quiet and the stall inspection above applies to a Fleet exactly as to a Swarm. Arming is part of the launch receipt; a launch that cannot arm the source records that gap rather than accepting the Fleet as supervised. Prove that a launched Fleet held in one turn past the stall-inspection threshold reads busy at the Hive, that the Fleet home's settings are unchanged by the launch, and that a launch unable to arm the source records the gap in its receipt. Source: [kunchenguid/firstmate#5342](https://github.com/kunchenguid/firstmate/pull/5342).

Every instruction or steer the Hive routes to a Fleet with a reply pending carries a configured reply age bound. When the bound passes without the request's correlated reply or recorded resolution, the Shadow records one escalation receipt and surfaces the held request to the Hive Mind in the Hive's own status, the Fleet row and History, naming the request and any open decision the Fleet itself is holding; it sends the Fleet nothing further, and a rule that quiets reposts while the Fleet is blocked on its own decision never quiets this escalation. The Fleet's handling receipt is acknowledgment only and neither stops the bound nor closes the escalation; the escalation closes when the correlated reply or the recorded resolution arrives. Prove that a routed request to a Fleet holding an open decision escalates exactly once at its bound with no second delivery, that a request the Fleet acknowledged but has not answered still escalates once at its bound, that it does not escalate under the bound, that another Fleet's open decision does not hold it, and that the later correlated reply or recorded resolution closes the escalation. Source: [kunchenguid/firstmate#7033](https://github.com/kunchenguid/firstmate/issues/7033).

Every event is correlated with its home and workspace, the applicable project and task generation, source and event identity, evidence revision, sequence and correlation/causation IDs, and carries occurred and observed times. Local receipts for an accepted or routed instruction reach the UI's projection as soon as they are durable; effects of remote execution still wait for a supported bounded observation. Initial and recovery snapshots establish current state without replaying old events as fresh action. Events are deduplicated by source, event and generation, bursts coalesce under a measured budget, and late or stale observations are labelled and kept in history. Write the observation and wake record durably before advancing its cursor. The supervisor drains wakes, reconciles current truth, performs idempotent actions, then acknowledges the exact handled sequence. Replaying after interruption may duplicate an alert but must not duplicate a launch, fix round or merge.

Worker status is evidence, not executable input. Validate schema, size, identity, allowed state transitions and the authenticated publisher; fetch full responses and reject truncation. Persisted observations, wakes, whole vendor or forge responses and worker status hold no value, under [Secrets](#secrets-hive-keeps-none): the Shadow's writer runs the owner's no-value check before the first byte; one that holds a value the check recognizes is refused whole, with the observation left unrecorded and its source read as unknown, and one that holds a value the check cannot recognize is kept exactly and is a found copy from the moment it is found. After a Harvest exists, prefer sanitized status comments or another verified receipt channel over commits to the code branch: the Claude measurement showed status-only commits cancelling and restarting a repository's own hosted checks. Private reports and Imperatives never use a public comment as a convenient transport.

### Context, capacity and safe checkpoints

The Shadow reads fresh context/resource observations through a capability-checked native interface, or a separately verified terminal observer bound to the owned session. Each observation includes source, timestamp, session generation and whether the value is measured, estimated or unknown. A supervision hook registration, cached footer or matching instruction file is not proof that context monitoring is running. Missing observation capability is explicit; it cannot be replaced by guessed usage or a destructive restart.

Configured thresholds produce a checkpoint request to the owned session, not a kill command. Claude saves through stow and reports readiness at a safe point; Codex retains its supported compaction/checkpoint behavior. The session owner records saved task/rule revisions, pending operations, branch custody and a checkpoint digest. The parent or authorized lifecycle owner verifies the exact runtime target and acknowledgment before restarting it. A stale lock, wrong target, failed save or busy gate blocks the transition and preserves work.

Resolve the effective idle-compaction policy across participating supervisor homes, not only the Hive's session. Role-specific exceptions must be explicit, and desired settings remain distinct from verified runtime behavior. Context thresholds and restart profiles are configuration; a restart reuses the ordinary policy resolver and records any authorized revision change instead of silently falling back to a cheaper or different model.

Resource floors use `hive-park` at a safe checkpoint; the Shadow records the clearing condition and wakes the owner under its policy. It does not terminate an active shared validation round or resume spend on a timer. Optional usage reports carry freshness and coverage, never an unconditional fresh label. Repeated handovers or scope-crossing signals can be recorded against configured fitness thresholds and presented as a decision; they do not autonomously split a Fleet or launch deferred research.

### Restart is a non-event

`hive-session-start` acquires the home lock, loads the Pool, charter, Imperatives, unresolved decisions, execution records and unacknowledged wakes, then schedules bounded live reconciliation. It loads Spoors and no value: a restarted process resolves each at its next use, under [Secrets](#secrets-hive-keeps-none). It does not relaunch everything in the journal. Reconcile only recorded direct reports, known vendor IDs, owned branches and known Harvests. After any outage the Shadow is re-armed before any wake is drained, so nothing is handled unobserved.

A deliberate stop is a recorded intent, not a crash. `hive-control stop` on a Fleet or other supervisor session persists a stop intent with its authority, reason and exact session generation before the session ends, and the Hive can request it for any Fleet it supervises. While the intent stands, `hive-session-start` reconciliation and the Shadow's recovery leave the session stopped: no relaunch, no crash alert and no retirement, while a session that ends without one is recovered as before. The intent names the Fleet's live Swarms and Lictors; the same word parks them at a safe checkpoint or leaves them with their records, worktrees and endpoints intact, and the Fleet overview keeps showing them under the stopped parent with the age of its last routed summary, as incomplete coverage rather than as retired or absent. An authorized start clears the intent only once the start has succeeded, and retiring a stopped session leaves no stop record for a later session that reuses its identity or route. Prove that a deliberately stopped Fleet stays stopped through Shadow recovery passes and a Hive restart while its Swarm stays shown with its last observation and age, that the same Fleet ending without an intent is relaunched, and that a failed start leaves the intent in place. Source: [kunchenguid/firstmate#7019](https://github.com/kunchenguid/firstmate/issues/7019).

Persist an operation intent before each external side effect and its receipt after success. If a process dies between them, query the exact existing branch, Harvest, session or task before retrying. If the service cannot prove whether an unacknowledged launch succeeded, keep it unknown and request recovery; do not promise exactly-once submission from an API that lacks that guarantee. Missing local endpoints likewise require the runtime's recovery-grade proof before replacement.

Restore poll deadlines, rate-limit backoff, subscription registrations, rule/projection revisions, accepted definitions, checkpoint and policy receipts, review-head bindings and pending cleanup transitions from disk. Re-read current forge state before decisions that depend on it. A completed remote task can be collected after the Mac returns; new dispatch, Synapse and Assimilation wait while the Mac is unavailable. A project's own hosted workflows and vendor event handling may continue independently; they are not the gate, and nothing they produce becomes readiness.

`hive-stow` saves unrecorded decisions, open work, handover facts and reusable knowledge to their proper private owners, curates stale memory, and checkpoints active operations. It does not substitute a conversation summary for task state or reconcile the whole Pool from memory. A failed save means the session is not reset-safe. Recovery reuses existing work, and guarded self-update never resets a dirty project to make versions align.

## Synapse on the Mac, with both reviewers

Synapse is local-first, and it runs over no-mistakes on the Mac as a long-lived plugin point. For every validated delivery, whether the head was built on the Mac or in the Void and whether it is published as a Harvest or kept as a local-only branch, the gate runs on the Mac and passes or fails there: the project's declared checks, a **Claude review**, an **Astra review** through local Codex, bounded fix rounds under one fix writer, and the readiness receipt. The plugin executes the checks, the reviews and the fix rounds; the `synapse` package owns the contract over it. Nothing in the gate needs GitHub Actions, a reviewer hosted on GitHub or a Harvest to exist. GitHub is one optional publisher of the gate's results and of the Harvest, with no authority of its own: a check or comment there is a copy of the Mac's receipt, never the verdict. Both reviewers stay on the Mac whatever place built the head; a Void placement of a Hunt changes nothing in the gate, and Codex Cloud's parked state and later retirement must not remove Astra from it. Both reviewer results are required by this path. No silently missing reviewer, empty diff or green publication status can count as a pass.

The Fleet stores the selected Synapse executor and its policy revision before dispatch. Hive's `synapse` package owns the Synapse contract described here for every validated delivery, whether the change was built locally or in the Void, over no-mistakes as the long-lived plugin point on the Mac. The [native local gate](#the-native-local-gate-after-the-pilot) is a later stage after the pilot; it replaces the plugin for a route only when it proves equivalent obligations, findings and custody, and qualification never migrates an active run. Record the actual executor rather than representing one as the other. Run one fix owner at a time; never let the plugin and another fixer, on the Mac or in the Void, concurrently rewrite the same branch.

| Pipeline obligation | Synapse over the plugin on the Mac |
| --- | --- |
| Intent and scope | Fleet supplies a review packet with the applicable acceptance criteria, authorized scope and source/head identities. The canonical Imperative remains private. |
| Fresh base and rebase | Read the live base, on the Mac for a local-only project and through gh for a published one, and check mergeability; commission a bounded repair for conflicts or an out-of-date base as required by project policy. No publisher is assumed to detect base-advance conflicts. |

The Synapse ledger owns retry count and which actor may write. |
| Tests and build | The project's declared test, build and smoke commands run from the Mac, by the plugin's test step, in the environment the project supplies. ### Validated local delivery, findings and custody

A local-only publication mode retains required review, tests, documentation and lint. For the plugin, the adapter uses its supported `no-mistakes axi run --skip push,pr,ci --intent "<authorized-intent>"` shape and records that publication/forge CI were intentionally excluded, not that validation was skipped. Qualify this mode in the project's actual initialization configuration before enabling it. The native local gate, after the pilot, must also qualify a local-only execution mode before replacing the plugin's route, using the same obligations and receipts without a GitHub publication requirement. An executor unable to validate the local project is a blocker; it cannot rewrite the Imperative to require only a clean branch.

A proof receipt binds the accepted specification and admission revisions, effective-rule digest, relevant environment/tool versions, tested scope, exact head/base, pipeline run/step, check producer and artifact references. Evidence belongs to that revision and run. A later code or requirement change invalidates affected proof unless the selected gate supplies a verified continuity result within its own contract. A report that tests passed is not a substitute for the current-head receipt.

For a held finding set, `hive-synapse collect` retrieves every finding in full, including ID, severity, location, description, action and authority where supplied. Persist the complete gate snapshot and digest with the run, step and head. The Swarm forwards the entire ask-user set to the Fleet; the Fleet applies its authority rules, escalates product/authority ambiguity to the Hive Mind and returns a disposition for every held finding. Decisions bind that snapshot and preserve the actual ruling. Missing or truncated findings, partial answers or a changed gate stay held; a general completion event cannot resolve them. The worker submits the authorized response and leaves every fix to the gate's selected executor. A finding or a log line that quotes a value found in a change is handled under [Secrets](#secrets-hive-keeps-none) either way: one the ledger writer's no-value check recognizes is refused whole before its first byte and the finding set stays held with the precise failure; one the check cannot recognize stays in the private ledger exactly as collected and is a found copy from the moment it is found, raising the incident. In both cases the published public-safe findings never carry it.

The no-mistakes plugin's branch-custody record is authoritative while it owns a run. Hive follows its offered reattach, guarded sync or recovery action and checks the resulting head; it never replaces the branch to discard a fix commit. A timed-out client call is distinct from a dead daemon or terminal failure. After publication or local validation, the Fleet verifies that its presented branch contains the pipeline's exact completed head before handing it to the Hive. Any divergence or uncertainty remains a concrete recovery blocker.

A finalizer on an integration branch is a choice a definition names for Hunts that cannot land apart; it is never the default and never required, and no Target is bounded by a count of Hunts or files. Its record names the participating Hunts, accepted specifications, integration owner and final-head validation policy. The finalizer has its own Synapse run and its own gate for findings, bounded by the one-run size of a Hunt and the gate's configured review-round limit as this document states them; naming one removes no Hunt's build and touched-test-target proof and waives nothing. It must establish fresh integrated-head evidence, and landing still uses the ordinary authority guards. No finalizer or plugin registration bypasses the decision intake, selected gate or forge authority contract.

### Checks and review contracts

The gate's checks run from the Mac on Synapse start and on every relevant head update, through the plugin's test, document and lint steps. Each project supplies executable test/build/smoke, formatter and linter commands in its validation configuration, along with the environment they run in and any project-specific machine, scheduling and capacity controls it needs; the plugin runs them in that environment, Hive collects revision-bound results and artifacts through the plugin's supported operations, and Hive provisions or administers none of that infrastructure. Record the actual platform, environment and tool versions in evidence. A credential a project's checks need belongs to the project and its environment and never passes through Hive, and the gate's own reviewers sign in by themselves, receive nothing from Hive and run only while their login is kept in the platform's store, under [Secrets](#secrets-hive-keeps-none). Hive's package test targets validate Hive itself and do not substitute for those project commands. Missing, cancelled, skipped, timed-out or failed required results do not pass. The Mac supplies native macOS proof. If a project requires proof on another platform, that requirement stays pending until the environment the project declares proves it; do not quietly reduce platform coverage, and do not turn that requirement into Hive-owned infrastructure. A project's own hosted workflows, where it keeps any, run on the forge against a published Harvest as that project's evidence: the gate neither starts, waits for nor reads them, and Assimilation reads their results at the current head wherever the Imperative states them as checks or the repository's own protection requires them. In its ordinary validation, at every head and in every fix round, a Hunt runs its build, the test targets its change touches and any long test that is that Hunt's own evidence, and it does not run the project's full suite. A Hunt lands through its own validation, as its Imperative's delivery records it: where validation is Synapse, through its own Synapse run, never a run shared with another Hunt; where the delivery is direct, through its stated checks and publication with no Synapse run. Three things are outside the ordinary validation of that sentence: the landing that completes a Target carries the Target's long tests; a definition may name an earlier test point, and a deployment or a showing to the Hive Mind is one; and the scheduled full run of a project's main branch is itself a Hunt, or a Prey that is a single Hunt, whose whole work is to run the full tests and report. A project's long test runs, the ones its test contract names as long, such as a full envelope, full flows, a browser suite, a release check or screen captures, run once per Target, at the head that lands the Target's last Prey. They are an obligation of the landing that completes the Target, on either delivery route: where that landing's validation is Synapse its Synapse obligations include them and its Assimilation is refused without the Synapse receipt that covers them; where its delivery is direct they are among its stated checks and its Assimilation is refused without those checks' result; and since a Target reads landed only when every one of its Prey has landed, a Target cannot read landed without them; no new record or state is needed. After that run, a later change re-runs only the long tests whose declared inputs it touched: each long test declares, in the project's test contract, what it reads, so the affected set is computed and never judged. A definition may name an earlier test point for its Target, and a deployment or a showing to the Hive Mind is always one. Every project runs its full tests on its main branch on a [schedule](#scheduled) of that project. No finalizer is required: the last Prey to land runs the long tests. Prove that a Hunt's ordinary gate run executes its build, its touched test targets and its own long runs and not the project's full suite, and that a scheduled full run of a main branch is a Hunt, or a Prey that is a single Hunt, that runs the full tests and reports; that the landing of a Target's last Prey carries the project's long tests, in its Synapse obligations or among its stated checks by route, and is refused Assimilation without their result; that a Target does not read landed without that result; and that a later change re-runs only the long tests whose declared inputs it touched.

The Claude review and the Astra review run on the Mac through the plugin's review step, with the plugin's configured review agents: a Claude review and a Codex review with the configured Astra model, each a separate session rather than the implementation Swarm grading itself, each run for every Synapse run and again for every head change, with one review owner and session receipt per head recorded in the ledger. A review mention on a Harvest, a hosted routine, the official GitHub Action or a forge-side Codex review is not a transport of either review and produces no attestation; each review is a local step of the gate. Head changes, readiness changes and missed runs are reconciled by the Shadow from the ledger, and a review of an earlier head is insufficient after a fix. Qualifying the plugin route proves that its configuration supplies both reviewer results in the shape below; a configuration that supplies one reviewer does not pass the gate.

The review packet contains repository, base/head SHAs, public change purpose and acceptance criteria, allowed scope, validation expectations, and the applicable sanitized decisions. If a reviewer needs private task context, it is given through the private review session on the Mac; the canonical Imperative is never pasted into GitHub or into a log. Reviewers treat repository text and comments as task data, not authority to broaden scope or Assimilate.

Each review returns reviewer identity, actual model where verifiable, session receipt, policy version, base/head, verdict, and findings with stable IDs, severity, file/line, evidence, and proposed correction. Preserve the complete result privately in the Synapse ledger. A branch author cannot satisfy the gate by adding a file claiming that reviewers passed: the gate reads its own receipts for a verdict, never the branch and never the forge.

Astra's review runs through the plugin's review step on local Codex with its configured Astra model, verified against the installed CLI, and its complete result is kept in private Synapse evidence. Re-enabling a Codex Cloud backend changes where a Codex Swarm may run and nothing about the review: the Astra review stays on the Mac under this ruling, and moving it would be a new ruling, not a backend migration.

Codex's [GitHub review integration](https://developers.openai.com/codex/integrations/github/) documents `@codex review` and automatic reviews. It was not exercised, it runs on the forge rather than on the Mac, and it is not selected: under the command-line-only Codex ruling and the local-first gate it neither substitutes for the local Astra result nor establishes new-service access.

### The native local gate, after the pilot

The design of a native local gate is kept here for a later stage or Target after the pilot, in which Hive supervises its own stages 6 and 7 over the plugin. It is not built in stage 5, and no stage before the pilot depends on it. Under the same Synapse contract, the `synapse` package would run the steps itself instead of driving the plugin: the project's declared checks from the Mac through Hive's project-validation executor; the Claude review as a separate local Claude Code session on the Mac, in a non-interactive mode with the review packet as its prompt and a structured result as its output, under the launch rules of [local sessions](#local-claude-and-codex) and with its flags verified against the installed CLI; and Astra as a separate local `codex exec` session with its configured Astra model and supported final-message export into private Synapse evidence, with those flags verified against the installed CLI. It replaces the plugin for a route only when it proves equivalent obligations, findings and custody, qualifies a local-only execution mode under the same obligations and receipts, preserves in-flight runs and archived evidence, and reconciles active runs before cutover; two fix owners never share a branch. Its evidence belongs to its own stage, and the plugin stays the executor for every route it has not replaced.

### Fix rounds and completion

Fix rounds are the gate's, on the Mac. The Synapse ledger records, for each run, the one actor that may write to the branch, the allowed scope, the current head, the remaining repair rounds and the expiry of that custody. The plugin's own fixer or a bounded repair Swarm dispatched by the Fleet is that actor; a repair Swarm takes a Hunt like any other, a Prey of its own that belongs to no Target, in the place chosen for it, on the Mac or in a Claude cloud session, and its committed or pushed head is collected and re-validated on the Mac. A fixer is launched with no credential, signs in by itself and runs only while its login is kept in the platform's store, and the sanitized output the Mac places in a repair Imperative carries no value, under [Secrets](#secrets-hive-keeps-none). The vendor's native Auto-fix, which the measured Claude session used to repair a failed check and a review comment on GitHub, is not a fixer of this gate: it reacts to a published copy of results rather than to the ledger, and it would be a second writer the gate does not own. The measurement remains evidence of the vendor's capability, and no subscription of that kind is registered on a Harvest Hive owns.

Resolve the repair budget, escalation point and exhausted-budget outcome as versioned configuration of the gate before dispatch, with the fixer's place recorded in each round; these are not one hard-coded round count. A genuine required defect stays blocking through every round; reaching a budget or escalation point produces a held decision or safe park, never an automatic waiver or success. A ruling on a finding chooses the smallest design that meets the accepted specification and never grows the mechanism under review; an expansion a finding asks for is filed as follow-up work; a ruling that added a mechanism nobody named is withdrawn at the next round that flags it; and the configured escalation round is the signal to simplify or escalate, never to start another. Deduplicate findings by head and finding; changing the head invalidates both reviewer passes and starts checks and reviews for the new head. A fixer must not weaken the checks to produce green. A new product choice, destructive action, ambiguous correction, inaccessible required log or exhausted round limit stops the fix and returns a concrete decision/blocker to the Fleet. A Swarm does not answer an ask-user finding about its own instructions.

Synapse is ready only when the project's complete declared check set, the documentation/lint obligations, both current-head reviews, and all required finding resolutions are present in the ledger for the exact head. Readiness is the Mac's head-bound receipt, which the Shadow independently verifies and records. Before Assimilation, stop further branch-writing repairs and confirm the fix writer's quiescence so an unnoticed late fix cannot race the reviewed head.

### Publication: GitHub as an optional publisher

Publication is a separate axis from validation, and GitHub is one optional publisher. Where the Imperative selects a Harvest, the Mac's publisher pushes the branch where a Void Swarm has not already pushed it and opens the Harvest through gh where none exists, or adopts the one it finds for that branch, including one a Swarm opened under its authorization. Where Synapse validation was selected, its trusted publisher, running under the configured publication identity with its own Spoor, looked up through `dispatch` and resolved through the launch primitive into each `gh` invocation and never written into the configuration, under [Secrets](#secrets-hive-keeps-none), also publishes, once readiness is recorded, the public-safe findings and a digest-backed attestation as a check bound to the exact head; a direct Harvest publishes no attestation. The publisher verifies receipt ownership before publishing and records the publication receipt with the Harvest's full URL and head. A local-only delivery publishes nothing and has the same gate.

A project may require the published attestation in its branch protection or rulesets, naming the publisher's expected GitHub identity, so that the forge refuses a landing the Mac has not passed. That is a guard the project chooses, not a transfer of authority: the attestation grants nothing, the forge's green is a copy of the Mac's receipt, and Assimilation reads the receipt, not the copy. The checks the Imperative states, and a repository's own required checks beyond the attestation, are read by Assimilation at the current head whether or not branch protection names any check; the repository's checks are its merge preconditions, read like any other repository rule. Nothing in the gate waits on the forge.

A Harvest's checks, comments and reviews are read back as published state and as task data. A human review comment on a Harvest reaches the Fleet as a finding to disposition through the ledger; it runs no round by itself, and nothing posted on a Harvest can mark the head ready. A published attestation that no longer matches the ledger, because the head moved or the ledger invalidated its proof, is stale: the new head carries no attestation until the Mac records readiness for it and the publisher publishes again, and display continuity on the forge never carries proof forward.

## Assimilation on the Mac

Only the Hive or the owning Fleet, acting through the Mac merge helper and within its recorded authority, can Assimilate a Harvest. A Swarm, Lictor, reviewer or Void subscription never merges. Local-only landing remains the Hive's guarded local operation.

`hive-assimilate <task-id> <harvest-url>` ports the checks and head binding of [the upstream merge helper](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/bin/fm-pr-merge.sh) and adds the Synapse evidence contract where Synapse validation was selected: the Mac's head-bound readiness receipt is the evidence, and the forge's state is read beside it. A direct Harvest carries its stated checks in place of that receipt, and Assimilation asks for the stated checks' result there and for the Synapse receipt only where the delivery's validation is Synapse; on either route the landing that completes a Target also carries the Target's long tests, in the Synapse obligations on the one and among the stated checks on the other. It must:

1. Validate the task generation, owning home and full forge URL; confirm the repository and target base match the Imperative. Acquire the task/authority lock and refuse an unresolved Mind's word hold.
2. Verify explicit Assimilation authority, or the Hive Mind's recorded autonomous posture for this project and scope. Away authority is checked at the moment of action; quiet mode does not imply away authority. Security-sensitive, destructive or irreversible changes retain their explicit-decision boundary.
3. Read the live Harvest: open, not draft, current head, current base, mergeable and conflict-free. A temporarily unknown mergeability result allows a bounded reread, not an optimistic merge.
4. Where Synapse validation was selected, read the Mac's readiness receipt for the current head: validated delivery's two reviewer attestations, the complete check set and every blocking-finding resolution must match that head and the required base, read from the Synapse ledger and never from a published copy. Then, for every Harvest, validated or direct, read the repository's own branch protection and active rulesets, including the producer identities they name, and take the checks the Imperative states: verify that every stated check and every repository-required check, the published attestation among them if the project requires it, has a result at the current head, whether or not protection names any check, and that all unwaived current checks are green. An unreadable requirements source blocks the operation. A repository rule can refuse a landing; none grants one.
5. Confirm collection/publication of the delivered commit and quiescence of any fix owner. Bind the merge request to the verified SHA, using the forge's supported expected-head guard corresponding to `--match-head-commit`. If the head or required evidence changes, stop and revalidate.
6. Read the forge back and record the actual merge SHA and time before claiming Assimilation. A queued request is pending, not landed; an unreadable response is unknown. Retain evidence for safe replay and cleanup.

An Assimilation is reported at once with the Harvest's full URL and the recorded merge SHA. A worker's claim that a Harvest landed is verified on the forge before it is repeated. A Harvest opened by a collaborator who is not a Swarm of Hive is never Assimilated by the Hive or a Fleet; landing it is the Hive Mind's own act.

The inherited attended exception for an explicitly named failing or missing check remains narrow: the Hive Mind must identify the concrete merge and check to waive. Record that exception and still enforce every other guard; neither autonomous posture nor away mode supplies a waiver. No worker can use administrative flags to skip Synapse. Repository identity, required-source readability and head binding are not inferred from a waiver.

`hive-assimilate-local <task-id>` ports the [local landing helper](https://github.com/kunchenguid/firstmate/blob/fb75c1f94170df7e0751147ea61afabcf5d4e104/bin/fm-merge-local.sh): verified local-only publication mode, required Synapse policy and passing proof at the exact accepted-specification/head revision, recorded Hive authority, released holds, clean owned branch and destination, and a fast-forward only. Divergence returns to a Swarm for reconciliation; it does not authorize a reset.

Cloud publication in the measurement used credentials that were not proven unable to merge. Holding a Spoor cannot widen authority over a protected base, under [Secrets](#secrets-hive-keeps-none); what an identity may do on the forge is what the forge grants it. Production enablement therefore needs a demonstrated permissions/ruleset arrangement that permits Swarms to publish branches and Harvests while reserving protected-base updates and Assimilation to the authorized Mac route. Where a project requires the published attestation, its producer identity must resist author spoofing. This is an implementation prerequisite, not a security property already established by the experiment.

After confirmed Assimilation, guarded synchronization refreshes the project copy. Cleanup verifies that all work is safely reachable or otherwise proven landed, confirms task/slot ownership, preserves unresolved decisions, and records the Pool transition before retiring execution records. A merge does not justify deleting uncommitted files or a sibling's copy.

### Requirement closure and worker retirement

Code Assimilation and requirement closure are separate recorded transitions. After verified landing, the owning Fleet's `hive-spec close` binds the landed head, accepted requirements, resolved findings and proof receipts, updates task completion, and folds or archives the accepted delta into the standing specification in the native Pool specification store. Preserve original rulings, amendments and evidence links. If store closure fails, retain a pending closure item and replay key; do not report the requirements landed merely because the code merged, and do not roll back a verified merge to hide the failed bookkeeping.

A Lictor report, card round, operator decision, specification delta and implementation task each have their own completion condition. The retirement queue checks all applicable receipts and unresolved holds before releasing owned execution resources. It can propose cleanup only from current authenticated state, not a timestamp-free status pattern, an old report or a PID file. Prove equivalence before retiring an existing cleanup mechanism; duplicate-looking scripts are not sufficient evidence that one is redundant.

A local Swarm's or Lictor's session and its worktree have separate lifetimes. Once the worker's done, failed, parked or blocked receipt is durable and its journal collected, `hive-control` ends the session on the ordinary exit path without waiting on cleanup; a blocked worker's later answer travels through the durable `hive-send` outbox to an authorized continuation in the same worktree, and a Fleet is persistent and never exited by this rule. The retirement queue's release then covers the worktree lease and reservation separately, under rule 3: a clean, landed copy is released, while a dirty, unlanded or uncertain copy keeps its lease and the task record gains a preserved-copy finding naming the worktree, what it holds and the follow-up that lands or explicitly discards it. A refused release never keeps a session alive, and repeated retirement passes over one worker are idempotent. Prove that a Swarm reporting done with an uncommitted file exits while its worktree stays leased with the file intact and the task shows the finding, that a later pass retries the refused release without a duplicate outcome, and that no Fleet session is exited by this rule. Source: [kunchenguid/firstmate#7015](https://github.com/kunchenguid/firstmate/issues/7015).

## Explicit decisions on inherited mismatches

These decisions resolve the workflow inventory's conflicts as part of this design. They describe Hive's target contract, not claims that the existing firstmate installation or external tools already enforce it.

| Mismatch | Decision taken by this design |
| --- | --- |

| Definition approval | The owning Fleet's supervisor accepts technical definitions within authorized intent. Only unresolved product or authority choices return to the Hive Mind. Old procedures requiring another operator approval for every technical definition are not inherited as mandatory ceremony. |
| Review rounds | Repair budgets and escalation points are configured policy of the gate on the Mac, with the fixer's place recorded in each round. | Inheritance and enforcement | Provision and verify required native capabilities and plugin wiring explicitly.
