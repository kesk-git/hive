# The Pool

The Pool is the durable work queue of a private home and the one authoritative store that admission, specifications, rules and task generations share, with one writer per transaction. This file is the contract of the `pool` package for stage 2 of the [ordered implementation plan](../docs/design.md#ordered-implementation-plan): where its records live, what each holds, what every operation does and refuses, how the execution place enters the contracts, how a legacy backlog comes in and goes out, and what `test-pool` proves. The decision intake is defined in its own definition of this stage, and the import of the Pool's upstream is planned in [import-plan-tasks-axi.md](import-plan-tasks-axi.md).

Owner: `pool`. Schemas: the eight records under [`schemas/records/`](schemas/records/) whose names begin `pool.`, and the operation bodies under [`schemas/ops/`](schemas/ops/) whose names begin `hive-pool.`, `hive-admit.`, `hive-imperative.`, `hive-spec.`, `hive-rule.` and `hive-memory.`. Proved by `test-contract` for the shapes and by `test-pool` for the behavior.

Nothing in this stage dispatches. The Pool records the place requested for an item's work and never assumes that the work has a worktree, a session or a clone.

## The store

Everything the Pool owns is under `pool/` in the home, in the five places [records.md](records.md#the-home) gives every package, and nowhere else:

| Path | Holds |
| --- | --- |
| `pool/records/item/<task_id>.json` | [Items](#items). |
| `pool/records/hold/<hold_id>.json` | [Holds](#holds). |
| `pool/records/admission/<admission_id>.json` | [Admission records](#admission). |
| `pool/records/imperative/<task_id>.json` | [Canonical Imperatives](#the-imperative), one per item, keyed by the item. |
| `pool/records/specification/<specification_id>.json` | [Specifications](#specifications). |
| `pool/records/rule/<rule_id>.json` | [Rules](#rules). |
| `pool/records/projection/<projection_id>.json` | [Knowledge projections](#generated-knowledge). |
| `pool/records/migration/<migration_id>.json` | [Legacy migrations](#legacy-import-and-export). |
| `pool/receipts/`, `pool/requests/`, `pool/tx/` | As [records.md](records.md#the-home) fixes them. |
| `pool/tmp/<request_id>.tmp` | The temporary file of a write in progress, as records.md fixes it. The next writer that takes the store's lock empties it. Nothing of the Pool's is read from it: a file here is never read as a record, a receipt, an intent or an outcome. |

- **One writer.** `hive-pool` and its five sibling command names are one executable, and every write to `pool/` is one transaction of that executable under `locks/pool.lock`, as [records.md](records.md#writing-several-records) fixes. No other package writes under `pool/`. No command offers a short form at a terminal: the request document is the one form.
- **The Mind's word.** An item can carry a hold of kind `word`. Such a hold is placed and released by the decision intake alone, which is defined in its own definition of this stage; `hive-pool hold` and `hive-pool release` refuse a `word` hold, and until that definition lands nothing releases one.
- **One reader.** Only `pool` reads under `pool/`. Every other package reads the Pool through `hive-pool read`, which returns whole records as a [projection](#reading-the-pool).
- **Never inside a repository.** Every `hive-pool` command refuses a home inside a Git working tree with `home_inside_repository` before it reads anything, as every command does. The Pool therefore cannot write into a project's code root, and `test-pool` proves it for the import, which is the one operation given a path that may lie inside a repository: that path is read and never written.
- **No secret value.** No record, receipt, event, intent or recorded outcome under `pool/` holds a secret value. Where a record must name a secret, it holds a `secret_ref` of [`records/pool.item.v1`](schemas/records/pool.item.v1.schema.json): the `spoor_` identifier of the secret's Spoor, and nothing else about the secret; its store, host, account identity and purpose are the Spoor record's, which `dispatch` owns and a later stage adds. The reference is neither the value nor a transferable authorization: holding one grants nothing, and the value is retrieved from the store at run time by whoever is entitled to it. The Imperative's `access.credentials` is the one place a credential is named, and the schema admits only references there. No field is a place for a value: a request whose text carries a value that Hive's secret-handling contract recognizes is refused whole, before anything is persisted, and nothing of it is applied. A value later found in a record is a found copy, handled as that contract says, by a sanitized incident that waits for the Hive Mind's word. How a value is recognized is that contract's, left undecided below. A request that puts a value where a reference belongs is `invalid`, and free text without one passes unchanged.

Their patterns are the `$defs` of [`records/pool.item.v1`](schemas/records/pool.item.v1.schema.json). The table in [identities.md](identities.md#identifier-form) and the registry in `contract/ids` are kept in step by a test of `test-contract`, so the rows are added there, with the constants, by the first change of the build and not by this definition. No prefix is registered for a [level](#levels): a Target is a Pool item and keeps the prefix every item has.

## Items

An item is one unit of work at one of three [levels](#levels), a Target, a Prey or a Hunt, or a decision held for the Hive Mind, which has no level. A Target and a Prey that holds Hunts describe work that others do; a Hunt, or a Prey without Hunts, is what one Swarm or Lictor works: a Swarm's change or a Lictor's report. An item describes work, never a persistent agent, and a Fleet is never an item. A decision item is shown in the Pool as a held item among the waiting decisions. Schema: [`records/pool.item.v1`](schemas/records/pool.item.v1.schema.json).

### Levels

- **`level`** is `target`, `prey` or `hunt`. `add` requires it for a new item whose deliverable is not a decision; a decision item carries none. An imported legacy item lacks it until its owner sets it with `update`, which sets a level only on an item that has none and refuses a change of an existing level with `pool.hierarchy`. Setting `target` on such an item is allowed only while it has no generation, no Imperative, no `parent` edge and no `schedule` and is `queued`, and is refused with `pool.hierarchy` otherwise, a schedule the owner clears first by an ordinary update; in the same transaction the Pool removes from it the members a Target never carries, `deliverable`, `placement_requested` and `delivery`, and reports them among the fields that changed. No patch syntax removes them: the removal is the defined effect of that level change. Setting `prey` or `hunt` keeps them, and the [parent rule](#levels) applies to the item as that patch leaves it.
- **A Target carries no deliverable, no requested placement, no delivery axes and no generations.** `hive-imperative create` refuses a Target with `pool.not_dispatchable`; so does a Prey that has a Hunt beneath it.
- **`wave`**, on a Target only, is the Wave's slug, title and ordinal on the project's roadmap, as the define step or the roadmap round recorded them. A Wave is the fourth level of the design's work hierarchy, an ordered group of Targets with an outcome on the project's roadmap; it is recorded as this grouping data on each of its Targets and has no worker, no Pool item of its own, no owner and no state of its own.
- **A schedule belongs to a Hunt or to a Prey that is a single Hunt**, never to a Target or to a Prey that holds Hunts, as the design says. `add` refuses a Target with a `schedule`, which its request schema states; `update` refuses a patch that sets one on a Target or on a Prey that has a Hunt beneath it with `pool.hierarchy`; and converting an item to a Target, and attaching a first Hunt beneath a Prey, are refused with `pool.hierarchy` while that item carries a schedule. The owner clears it first by an ordinary update, with `clear_schedule`.
- **The parent rule.** A Hunt has exactly one `parent` edge, to a Prey. A Prey has at most one, to a Target; a Prey with none belongs to no Target, as a follow-up, a residue fix or a lone Lictor's work does. A Target has none. `add` and `update` check the rule on the item as the request leaves it and refuse a violation with `pool.hierarchy`: any other pair of levels, a second `parent` edge, a Hunt left without one, a `parent` edge on a Target, a Hunt attached to a Prey that carries the completion marker, is in flight or has an open generation, which the owner first reopens by the transition that already exists, and a first Hunt attached to a Prey that carries a schedule, which the owner first clears by an ordinary update; no conversion is defined. An item's `parent` edge is set, replaced or removed only while that item and every item beneath it is queued, has no Imperative and has never opened a generation, and is refused with `pool.hierarchy` otherwise; no admitted work can change definition by a move. When a `parent` edge is set or changed, the Pool recomputes the `definition` hold, and not the `definition` state, of the moved item and of each item beneath it by the rule that places it at creation: the hold is present exactly when an accepted specification is required and the item has no effective specification. An imported item with no level is exempt until its owner sets its level, and the rule applies to it from that update on. A decision item that is not imported takes a deliverable of `swarm` or `lictor` only in an `update` that sets its `level` too, and is refused with `pool.hierarchy` otherwise. A Target's `blocked-by` edges name the Targets it depends on.

### State

`state` is one of `queued`, `in-flight`, `done` and `archived`. The first three are the three sections of the legacy backlog and keep its transitions; `archived` is a retired item, never a deleted one.

`definition` is kept beside `state`: `not-required`, `needed`, `defining` or `accepted`. The design's five-step passage is the two read together: *definition-needed* and *defining* are queued items with those definitions, *accepted* is a queued item whose definition is accepted, *building* is in-flight and *delivered* is done. Holds are kept apart from both, as separate records. On a Target, `needed`, `defining` and `accepted` are its define step; a Prey or a Hunt resolves its specification through its parent by the rule of [Specifications](#specifications) and needs none of its own unless the Fleet requires one.

| From | To | Through | Refused when |
| --- | --- | --- | --- |
| `queued` | `in-flight` | `open-generation`, or `transition` | an active hold stands on the item or on an ancestor: `held`, naming it; a `blocked-by` edge of the item or of an ancestor names an item of this Pool that has not [landed](#derived-facts): `pool.blocked`; the item [needs an accepted specification](#specifications) and has no effective specification: `pool.specification_unaccepted`; `deliverable` is `decision`: `pool.not_dispatchable`; through `open-generation`, the item is a Target or a Prey that has a Hunt beneath it: `pool.not_dispatchable` |
| `queued`, `in-flight` | `done` | `transition` | a generation is open: `pool.generation_open`; the item is a Target, or a Prey that has a Hunt beneath it, whose landing is [derived](#derived-facts): `pool.derived_state`; a Prey with no Hunt completes directly |
| `in-flight` | `queued` | `transition` | a generation is open: `pool.generation_open` |
| `done` | `queued`, `in-flight` | `transition` (reopen) | as for the state entered |
| any but `archived` | `archived` | `transition` | an item that has not landed has a dependent whose `blocked-by` edge names it and that has not landed and is not archived: `pool.dependency_active`; a generation is open: `pool.generation_open` |
| `archived` | anything | | always: `pool.state_transition` |

- `done` sets the completion marker `completed` and `closed_at`, from the request's `at` or the clock, and adds the request's `evidence` to `links`. The marker and the closing time are two facts: the marker is what the landing of a leaf reads, and a dependency reads the landing, and the time is evidence of when. Only a leaf, a Hunt or a Prey with no Hunt, or an item that has no level, is set done: a Target and a Prey with a Hunt beneath it land from the items beneath them. A reopen clears the marker and the time; archiving a done item keeps both, which is how its completion survives archival, and an item archived without having been done has neither. A completion without evidence is allowed and is what it says: nothing in the Pool claims a landing, a report or a Harvest that no link names.
- An unreleased hold survives `done` and `archived`: the hold record stays active and is released only as its kind says. Cleanup, at a later stage, reads the hold and keeps what it names.
- `transition` to `in-flight` without a generation exists for the legacy import and for tests; dispatch at stage 4 goes through `open-generation`. The return from `in-flight` to `queued` is the upstream's reopen of an item that was started and not finished, allowed when the item has no open generation.

### What an item carries

| Field | Meaning and rule |
| --- | --- |
| scope fields | The [scope](identities.md#scope). The Hive's own work is `hive`; a Fleet's is `project`, or `workspace` for work of no single project. `clone_id` is given only where the work is bound to one registered clone; the Pool never requires it. |
| `title`, `body` | Kept exactly as written. |
| `level` | The [level](#levels): `target`, `prey` or `hunt`. Absent on a decision item, and on an imported legacy item until its owner sets it. |
| `wave` | On a Target only: the Wave's `slug`, `title` and `ordinal` on the project's roadmap, as the define step or the roadmap round recorded them. |
| `deliverable` | `swarm`, `lictor` or `decision`. Absent until intake assigns it, and absent on a Target; a decision item never dispatches. |
| `class` | The dispatch class, 0 to 7. Absent until intake assigns it. |
| `priority` | 0 to 4, as the legacy format carries it. |
| `placement_requested` | The [execution place](#the-execution-place). `policy` when the request leaves it out. A Target has none. |
| `delivery` | The three delivery axes, declared separately: `validation` (`synapse` or `direct`), `publication` (`harvest` or `local-only`), `assimilation` (`word` or `posture`). A change of publication cannot remove validation: the two are independent fields, and `local-only` with `synapse` is an ordinary combination. A Target has none. |
| `specification_required`, `specification` | Whether build dispatch needs an accepted specification, and the accepted revision bound by identity, revision and digest. Only `hive-spec accept` sets `specification`, and an invalidation clears it. What admission, rendering and dispatch read is the item's [effective specification](#specifications), which is its own binding or its parent's. |
| `deps` | `blocked-by`, `parent` and `discovered-from` edges to items of the same Pool, each with free-text `reason` that is carried and never read for state. A new `blocked-by` edge must name an item that exists; a dangling edge found in a legacy file is kept and treated as resolved, as the upstream does. A `parent` edge obeys the [parent rule](#levels); a Target's `blocked-by` edges name the Targets it depends on. |
| `links` | A Harvest by full URL, a report or document by URL or path, or a record by reference. |
| `schedule` | A `gate` with its not-before time or a `recurrence` with its interval and anchor, as declared on the item, each a wall-clock time with its zone. The item owns the work; the dispatcher's schedule record, at stage 4, carries the runs. A date here dispatches nothing. Carried by a Hunt or by a Prey with no Hunt beneath it; a Target and a Prey that holds Hunts have none, by the [schedule rule](#levels). |
| `generations` | Every [generation](#generations) opened on the item. Empty on a Target, which has none. |
| `handoff` | The one handoff to a child Fleet, with its evidence, instead of a second competing task. Written by the parent on the receipt stage 4's `hive-fleet route` returns. |
| `legacy` | The legacy identity, kind, repo and free-form fields, verbatim, with the migration that created the item. Never read as authority. |

`add` mints the `task_id`, writes the item and the `pool.item.added` receipt, requires `level` for a new item whose deliverable is not a decision, and refuses a `blocked-by` edge to an item that does not exist (`pool.dependency_missing`) and a `parent` edge or an item that breaks the [parent rule](#levels) (`pool.hierarchy`). `update` applies a patch and reports the fields that changed, `level` and `wave` among them, and refuses a patch that leaves the item breaking the parent rule, or that changes a decision item into work without a level, the same way, one that removes a Hunt's only `parent` edge included; a patch that sets `level` on an item that has none is the conversion [Levels](#levels) defines, and the members it removes are reported with the rest; a patch that changes nothing writes nothing, raises no revision and returns no receipt. A change of `placement_requested` after a generation opened does not touch that generation; the next one reads it.

### Derived facts

`blocked`, `held`, `ready` and `landed` are never stored. `hive-pool read` computes them at the moment of the read.

**Effective completion** is defined here once, and `landed` is it. A leaf, which is a Hunt or a Prey with no Hunt beneath it, or an item that has no level, has landed when it carries the completion marker `completed`, which its own transition to done sets, which a done item has and keeps through archival and which a reopen clears; the closing time is never what lands it. A Prey with Hunts has landed when at least one Hunt points at it and every Hunt that points at it has landed. A Target has landed when at least one Prey points at it and every Prey that points at it has landed, so a Target with no Prey has never landed. A marker on an item that has an item beneath it is not read. No marker is stored for a Target or a Prey with Hunts.

Every place that asks whether a blocker is satisfied reads `landed`: the `blocked` and `ready` facts, the guard at the transition out of the queue and the guard before a generation opens. A blocker that has not landed satisfies nothing, an archived leaf that was never done included, and a blocker reopened, or one with an item beneath it reopened, has not landed again; a blocker whose closing time is not known has landed as any other does. An edge to an item that does not exist is resolved.

**A container's dependencies and holds bind every item beneath it.** An item's effective blockers are its own `blocked-by` edges and those of each ancestor through its `parent` edges, and its effective holds are its own active holds and each ancestor's, the `definition` hold of a Target included until its define step has landed and `hive-spec accept` has released it. The `blocked`, `held` and `ready` facts, the read request's `ready` predicate, the guard at the transition out of the queue and the guard before a generation opens all read these effective facts, and `active_blockers` and `active_holds` list them. A hold on a Target therefore stops its Prey and Hunts until it is released, and a Target that depends on another does not start its work until that one has landed.

- **`blocked`:** the item has not landed and it, or any ancestor, has a `blocked-by` edge that names an item of this Pool that has not landed.
- **`held`:** it, or any ancestor, has a hold that is active and, for a dated hold other than a `word` hold, its `until` has not passed; a `word` hold stays in force whatever date it carries.
- **`ready`:** the item is queued, not blocked, not held, not a decision item, not a Target and not a Prey that has a Hunt beneath it. The last three are never dispatched, so they are never ready, whether or not they have landed.
- **`building`:** a Target is building when any item beneath it is in flight.

A `transition` to done on a Target, or on a Prey that has a Hunt beneath it, is refused with `pool.derived_state`: their landing is read from the items beneath them. Completing the last Hunt of a Prey lands the Prey, which can land its Target, which then satisfies the `blocked-by` edge of a Target that depended on it.

### Generations

A generation is one execution of an item. It is opened in the Pool before anything is launched and closed when the caller establishes how it ended, and the Pool records only what it is told: the number, the place requested at the moment it opened, the Imperative revision and admission it runs under, and the outcome and evidence the closer named. Execution state, the backend, the resolved place and the lease belong to the dispatcher's and the Spawning Pool's records at later stages, bound to the item by `task_id` and `generation`.

- `open-generation` applies the dispatch guards of the transition table at every open, for an in-flight item as for a queued one: an active hold on the item or on an ancestor (`held`, a `word` hold whatever its date included), a blocker of the item or of an ancestor that has not landed (`pool.blocked`), a required specification that has no effective specification (`pool.specification_unaccepted`), an Imperative whose `standard.criteria` differs from the item's current effective specification (`pool.imperative_stale`), and a decision item, a Target or a Prey that has a Hunt beneath it (`pool.not_dispatchable`); a failed generation that left the item in-flight, followed by the reopening of a blocker, therefore cannot open another until the blocker lands again. It requires an admission in state `admitted` whose last check read the item's current revision and the Imperative's current revision; a changed item or Imperative since then is `pool.admission_stale`, and the caller checks again. It numbers the generation one above the last, snapshots `placement_requested`, moves a queued item to in-flight in the same transaction, and writes `pool.generation.opened`. At most one generation is open at a time: a second is `pool.generation_open`.
- `close-generation` records the outcome the caller reports from its own receipts: `delivered`, `failed`, `stopped`, `superseded` or `unknown`, with the receipt or record as `closed_by`. `unknown` is an outcome and never a success. Closing changes the item's state not at all; delivery is a `transition` with its own evidence.
- A change of place is a new generation, never an edit: the snapshot in a closed generation is never changed.

The Spawning Pool at stage 3 reads the generation as the Pool records it: `task_id`, `generation` and `placement_requested`. A generation whose requested place is `claude-cloud-session` or, once it is ever admitted, `codex-cloud`, holds no lease of its own; the Spawning Pool leaves room for it and for the collection lease taken on its behalf.

## Holds

A hold keeps an item, and every item beneath it, out of ready and out of dispatch. Each is its own record, so that a response can name it in `error.hold`, the Shadow can key a wake on it, and it can outlive the item's completion. Schema: [`records/pool.hold.v1`](schemas/records/pool.hold.v1.schema.json).

| Kind | Placed by | Released by |
| --- | --- | --- |
| `word` | The decision intake alone | The decision intake alone; `hive-pool hold` and `hive-pool release` refuse it |
| `admission` | `hive-admit check`, with a `reason_code` | A later `hive-admit check` that admits |
| `definition` | The Pool, when an item that needs a specification is added and has no effective specification, or when an acceptance it carries or resolves through is invalidated | `hive-spec accept` |
| `parked`, `external`, `resource`, `future` | `hive-pool hold`, with a reason; `future` with its `until` | `hive-pool release` |

- A dated hold other than a `word` hold is inactive on and after its `until` and stays `active` as a record until released; a `word` hold is never made inactive by a date: its date, an imported one included, is a revisit date that readers show and nothing more, and the hold stays effective until the decision intake releases it; the Shadow reads active holds with `due_before` and wakes the owner, who releases or re-presents. A hold's `until` is a wall-clock time with its zone; a legacy date is read at the start of that day in the import's zone and kept beside it as written.
- Releasing a hold writes `pool.hold.released` with the release's evidence and never deletes the record.
- A legacy hold for the operator is imported as a `word` hold and is the decision intake's from then on.

## The execution place

Where an item's work runs is a choice made for that item. The Pool records the request, the Imperative renders it, admission checks it. Resolution, launch and the binding of the resolved place into the execution record are stage 4's.

`placement_requested` is one of:

| Value | Meaning |
| --- | --- |
| `mac` | On the operator's machine, the one the Hive runs on, whether it runs macOS, Windows or Linux. The value keeps its name on every platform: renaming it would be a major change, and none is made. |
| `claude-cloud-session` | In a Claude cloud session. |
| `policy` | Left to the policy resolver. |
| `codex-cloud` | Codex Cloud, which is out of Hive's scope until it can be used the way a Claude cloud session is: a named value that admission refuses with `pool.placement_parked`, unconditionally. The code keeps its name, since renaming it would be a major change. It is never substituted and never silently changed. |

The UI labels `mac`, `claude-cloud-session`, `policy` and `codex-cloud` Local, Claude cloud session, By policy and Codex Cloud (out of scope), with the same four labels on every platform. Local names the place on the operator's own machine, whichever of the three it runs; the value `mac` keeps its name.

**How the refusal is known.** At stage 2 the refusal of `codex-cloud` is written into `hive-admit check` itself: no rule record, policy request, configuration value, environment value, authority reference or `approve` can admit it, and `test-pool` proves that a check with each of those present still refuses. The design fixes what would bring Codex Cloud into scope, in [Codex: three backends and a migration boundary](../docs/design.md#codex-three-backends-and-a-migration-boundary) and [Enabling and retiring a Codex backend](../docs/design.md#enabling-and-retiring-a-codex-backend): a supported command-line route that honors model selection, a controlled replay of the full readiness contract, and the Hive Mind's recorded, authorized configuration change, with "an accepted default-model task" unable to bring it into scope. In this specification that is one change, made by a stage that builds a Codex Cloud backend behind the adapter contract once Codex Cloud is back in scope, which no stage of the current plan does: a minor change of this file and of the check that replaces the unconditional refusal with a read of that backend's capability record, which stage 4 defines, in state ready, and the Hive Mind's ruling by reference as that record names it. Until that change is accepted and built, every `codex-cloud` request is refused, whatever else a home holds.

- **Setup renders the Placement axis from the item.** `hive-imperative create` and `revise` take no placement: the command copies `placement_requested` at the item revision it read into `setup.placement`, with that revision. The author cannot set it; the inspector and the rendered text show it as the item's.
- **Admission reads the item and the project.** `hive-admit check` checks the place named in its request, the item's requested place or a place the caller's policy resolved, against the project's repository binding read from the identity records: a Void placement (`claude-cloud-session` or `codex-cloud`) for a `local-only` project is refused with `pool.placement_local_only`; a Void placement whose source branch the caller's evidence does not show pushed is held with reason code `source_branch_not_pushed`; `codex-cloud` is refused as above. `mac` and `policy` pass this check for any project. The Pool runs no Git: the branch's state is evidence the caller supplies, and absent evidence is unknown, which holds.
- **The Imperative and the item agree.** A check compares the Imperative's `setup.placement` with the item's current `placement_requested`; a difference is `pool.imperative_stale` and the caller revises. A harness that cannot run in the place is a contradiction: `codex` with `claude-cloud-session` is refused with `pool.setup_contradiction`.

**A generation placed in a Claude cloud session.** The Pool records the place and nothing of the model: model, effort and the resolved place are the resolver's, as `render` says. What stage 4 does with a generation whose requested place is `claude-cloud-session` is stated in the design's [Claude in the Void](../docs/design.md#claude-in-the-void), and this contract records it against the place it defines. The launch passes the Hunt's class as the explicit model and effort of the effective profile resolved for it, and a launch that names no model is refused, never left to the vendor's default. The Imperative's Definition of done requires of the session a record of its own model and effort, in a status file on its branch, which the Pool renders as its author wrote it and does not check. Collection verifies the collected commits against that record, and reads a recorded model or effort that differs from the class, or a record that is missing, as a finding and never as a clean collection. Nothing the session reports of its own checks stands for a check bound to the operator's machine, where Synapse runs over the collected head whatever the session reported. The contradiction check above already keeps a harness of another vendor out of this place. No Pool record changes for any of it: the place keeps its name and its meaning, the generation records the place requested and the outcome the closer names, and the comparison and its finding are the dispatcher's, in its collection receipt.

## Admission

Admission preserves the original request, checks the Imperative's single schema and records a receipt bound to the Imperative revision and digest and the authority used. Schema: [`records/pool.admission.v1`](schemas/records/pool.admission.v1.schema.json).

- `create` records the request immutably: the words as given, who gave them, the authority they carried and the Imperative revision they concern, which must be current. It checks nothing. Receipt: `pool.admission.created`.
- `check` runs the checks below against the Imperative revision, the item as it stands and the evidence in the request, appends the check to the record and writes one receipt: `pool.admission.admitted`, `pool.admission.refused` or `pool.admission.held`. The response status follows: `ok`, `refused` with the first finding's code, or `held` with the hold in `error.hold`. A check may be run as often as a launch path needs; every launch path at stage 4 runs it, and a later check with new evidence may admit what an earlier one held. An earlier check is never changed.
- `approve` records a required ruling: the envelope's authority must be of kind `word`, which the Pool verifies by the decision intake's check that the operator's word stands, defined in its own definition of this stage; until that definition lands a `word` authority, like any other kind, is `authority_insufficient`. It records the approval and nothing else; the caller runs `check` again, which reads it. Receipt: `pool.admission.approved`.

The checks, in order; the first that does not pass fixes the result, and every finding is recorded:

| Check | Fails as |
| --- | --- |
| Object, Standard, Output and Boundary are present and non-empty | `invalid` at `create`: the schema requires them. A record that lost one is `record_malformed`. |
| No field is a guess | `held`, reason code `field_guess`, finding `pool.admission_guess` naming the field, its question and its consequence. |
| The Imperative is current and agrees with the item | `refused`, `pool.imperative_stale` |
| Harness and place do not contradict | `refused`, `pool.setup_contradiction` |
| The item needs an accepted specification and its effective specification is the one at the Imperative's `standard.criteria`; an item that has an effective specification, needed or not, must name it | `refused`, `pool.specification_unaccepted`; a Standard naming a revision other than the item's effective specification is `pool.criteria_mismatch` |
| The place is admissible for the project and the backend is not parked | `refused`, `pool.placement_parked` or `pool.placement_local_only` |
| A Void place has a pushed source branch | `held`, reason code `source_branch_not_pushed` |
| Each sensitive boundary (`spend`, `deletion`, `security`, `publication`) has explicit, applicable authority: an approval on the record, or the request's own authority verified by the Pool | `held`, reason code `authority_required`, finding `pool.authority_required` |
| Validation and publication of the Output agree with the item's `delivery`; `harvest` is not asked of a `local-only` project | `refused`, `pool.delivery_mismatch` or `pool.publication_needs_forge` |

The authority kind admission can verify at stage 2 is `rule`, because its record is the Pool's; a `word` authority waits for the decision intake's check, and is `authority_insufficient` until that definition lands. A `posture`, `charter` or `instruction` reference names a record of `dispatch`, which stage 4 defines; until that stage adds the route by which admission accepts one, such a reference is `authority_insufficient` for a sensitive boundary. High-confidence dispatch within existing authority needs no authority reference at all: `none` passes every check but the sensitive ones.

## The Imperative

The canonical Imperative is one record per item, with every revision whole, and it never enters a repository, a Harvest, a comment or a log. Schema: [`records/pool.imperative.v1`](schemas/records/pool.imperative.v1.schema.json).

A revision holds the dispatch class and the four sections of the design: **Task** (the Hive Mind's intent kept apart, then Object and Standard), **Setup**, **Rules** (the Boundary, the validation commands and the channels, and in the rendered text the playbook of the revision's class) and **Definition of done** (Output and the stopping point). Object, Standard, Output and Boundary are typed fields inside their sections and each carries a `confidence`: `high`, or `guess` with the question and consequence admission holds on. There is no four-part block beside the Imperative and no copy of it anywhere.

- **The Standard carries criteria by reference.** `standard.criteria` names the accepted specification revision; `render` reads that revision, the item's effective specification, from the Pool and writes its criteria into the Standard's text. There is no editable copy of the criteria in the Imperative, and a revision whose `standard.criteria` differs from the item's effective specification does not pass admission.
- **Setup holds the Placement axis** copied from the item, the repository binding copied from the project record at authoring (or given, for the Hive's own projectless work), the branches with their revisions once known, the role, the harness, dependencies, tools, access and isolation assertions. Setup implements the Boundary and cannot widen it; a validation command is an argument vector and never a line of shell.
- **`create`** writes revision 1; **`revise`** writes the next, whole, with the reason, under the record's expected revision. `create` refuses a Target, and a Prey that has a Hunt beneath it, with `pool.not_dispatchable`: they describe work that others do and are never worked themselves. Both copy the placement and the repository, compute the revision's digest over the canonical form of its class and four sections, and write `pool.imperative.revised`. Steering that changes scope revises first; the caller then repeats admission.
- **`render`** is read-only and deterministic: the same revision, the same specification revision, the same rules in force for the revision's class and the same renderer version give the same text and digest, and `test-pool` proves it. The text opens with the worker role boundary, then the four sections in order with their headings, the Standard's criteria rendered from the specification, and the Placement axis in Setup. In Rules, after the Boundary and under a heading of its own, it writes the playbook of the revision's class, as the design's [Eight dispatch classes](../docs/design.md#eight-dispatch-classes) states: the rules the resolver gives for the Imperative's scope and the class's role, `class-0` to `class-7`, at the instant of rendering, in the resolver's order, each as its rule line with its source and revision. The playbook is no record of its own and no member of the revision: it is read from the rule store at each rendering, so the rendered digest that `deliver` records binds the lines one generation was given. A conflict among those rules refuses the rendering with `pool.rule_conflict`, since an Imperative whose playbook is unresolved is not delivered. It returns the text, its digest and size, and the launch parameters the Imperative itself fixes: role, harness, requested place, class, validation and publication. Model, effort and the resolved place are the resolver's and are not here.
- **`deliver`** records exactly what one open generation was given: the revision, the rendered digest and size, the renderer version, the transport and the dispatcher's receipt. It is stage 4's to call and stage 2's to build and prove with a test caller. Receipt: `pool.imperative.delivered`.

## Specifications

A specification is a native record of what a change must satisfy: prose and acceptance criteria, each criterion with a stable identity and the evidence that proves it. Schema: [`records/pool.specification.v1`](schemas/records/pool.specification.v1.schema.json). A sufficiently complete existing specification is referenced by identity and need not be rewritten for every item.

- **The effective specification** is resolved here and nowhere else, and every sentence of this file that speaks of an item's specification reads it. An item's effective specification is its own accepted binding, its `specification`, where it has one, and otherwise the effective specification of its one parent, a Hunt reading its Prey and a Prey its Target; an item with no binding on its path to the top, a Prey that has no parent included, has none. An item needs an accepted specification when its own `specification_required` is true or when the item it resolves through, its parent, needs one. Admission, the rendering of an Imperative's Standard and the guard before a generation opens read the effective specification, and the Imperative's `standard.criteria` must equal it. When an acceptance is invalidated, every item that resolves its effective specification through it, at any depth, is treated as the contract treats an item that carried it: a dispatchable one, a Hunt or a Prey with no Hunt, that has not landed returns to `defining` and receives a `definition` hold, and nothing else of it changes; an item with a binding of its own is untouched by its ancestor's invalidation. `accept` for the ancestor releases those holds and returns the items' `definition` to `accepted`. An item added beneath a parent that resolves an effective specification takes `definition` `accepted` when it needs one and receives no `definition` hold; an item that needs one and has none takes `needed` and the hold.
- **`define`** writes revision 1 of a new specification or the next revision of an existing one, whole, with the criteria whose identity or text changed listed in `changed_criteria`. Items named in `task_ids` move to `definition` `defining`, except an item whose accepted binding to this specification survives the revision, because its criteria are unchanged against the revision it is bound to: it keeps `accepted` and its binding, so a prose-only revision never makes a dispatchable item undispatchable. Invalidation is decided per binding, not from the last acceptance: `define` finds every item whose `specification` names this specification, whichever revision it is bound to, and compares the new revision's criteria, by identity, text and evidence, with the criteria of the revision that item is bound to. Where they differ, that item's acceptance is marked `invalidated`, the item loses its `specification`, returns to `defining` and receives a `definition` hold, and the items that resolve through it are treated as the first bullet says; an item bound to a revision whose criteria the new one leaves unchanged keeps its binding. Nothing else of those items changes, so a worker's target is never silently changed. `changed_criteria` lists the difference from the revision before and is information: invalidation does not read it, so a revision that changes nothing against the revision before it still invalidates an item bound to an earlier revision it differs from. Receipts: `pool.specification.defined`, and `pool.specification.invalidated` for each acceptance invalidated.
- **`accept`** appends the acceptance of the current revision for one item by the supervisor that called, one acceptance per item: the Fleet's for its workspace, the Hive's for its own. It binds the revision by identity, revision and digest into the item's `specification`, sets the item's `definition` to `accepted`, releases its `definition` hold and those of the items that resolve through it. Technical acceptance settles no product choice, and a `word` hold the item carries stays until the decision intake releases it. Receipt: `pool.specification.accepted`.
- **`close`** records, after a verified landing, that the accepted requirements were met: the landed head, the landing receipt, the proof receipts and the resolved findings the caller names, bound to the accepted revision, item and generation. It is one transaction; if it does not commit, the landing stands and the closure stays pending for replay under the same request, and nothing reports the requirements landed because the code merged. Receipt: `pool.specification.closed`. Folding the accepted delta into a standing specification is a `define` of that specification that cites the closure.

`hive-admit check` and `hive-imperative render` read the specification through the Pool's own store; no other package reads it but through `hive-pool read`.

## Rules

The rule store separates original words from their operational interpretation and keeps both. Schema: [`records/pool.rule.v1`](schemas/records/pool.rule.v1.schema.json).

A rule carries its `subject` (a fixed key for what it governs), the `words` verbatim, its `origin`, its scope from the envelope (Hive, workspace, project, and a task generation where it rides an Imperative revision), the roles it `applies` to, one `rule_line` supplied by the recorder, its `effective_at`, its applying `authority` with the intake receipt, and for a temporary rule an `expires_at`, a `lift` condition naming a receipt kind and subject, or both. A temporary rule is this same record and no second mechanism.

- **`record`** appends a rule and writes `pool.rule.recorded`. The words and dates given are never changed afterwards. A rule that `changes` a standing rule names it by identity and revision with the relation `supersedes` or `qualifies`; the standing rule is never edited, nothing is recorded on it and its status does not change. The relation is read at each resolution and is never a retirement: see `resolve`.
- **`amend`** appends an attributed amendment of the rule's operation: `extend` or `end` with a new expiry time, `lift` with the receipt that met the lift condition, or `note`. The receipt must be of the kind and about the subject the condition named. A rule lifted on another package's receipt is lifted on evidence the caller supplies: `hive-rule amend` carries that receipt whole in its request, the Pool checks its kind and its subject against the lift condition and records it with the lift, and the Pool calls nothing and reads no other package's store. A supersession is not an amendment; to retire a standing rule for good, `end` it or record a standing rule that supersedes it. The original `expires_at` stays and the latest amendment's `new_expires_at` is what the resolver uses. Receipt: `pool.rule.amended`, or `pool.rule.lifted` for a lift.
- **`expire`** records that the expiry was noticed and honoured, with the time it was noticed; before the expiry time it is refused with `pool.rule_not_expired`, and a second call returns the first receipt. Receipt: `pool.rule.expired`. The receipt records the noticing; the exclusion happened by the clock.
- **`resolve`** computes, read-only, the rules effective for the envelope's scope, a role and an instant: it collects rules in force at `at` whose scope is the Hive, the workspace, the project where the scope names one, and the task generation where the request names one; drops those that do not apply to the role, are not yet effective, are lifted or ended, or are past their expiry time by the clock, whether or not an expiry receipt exists, and so leaves the **live set**; then drops a rule of the live set that a rule of the live set names with `supersedes`, so that a superseding rule retires the one it supersedes only while it is itself in force for this scope, role and instant: a temporary rule that has expired, has been lifted or is not yet effective leaves the standing rule in force; applies inheritance by letting the narrower scope govern a subject the wider also governs, except that a rule of the live set which a narrower live rule names with `qualifies` stays in force beside it, whatever the scopes, so a project rule that qualifies a workspace rule adds to it and does not replace it; and reports a **conflict** for a subject two rules govern at one scope when neither names the other in `changes`: a rule that `qualifies` another is in force beside it and is no conflict. It returns the rules in order, each as its rule line with the source and revision appended, the conflicts, what was excluded and why, and the **resolved-rule digest**, the digest of the canonical form of the rules array, present only when there is no conflict. A caller whose action depends on a conflicted subject holds that action; the resolver decides nothing.
- A rule whose `applies` names a class role, `class-0` to `class-7`, belongs to that class's playbook: its steps, its checks and its stopping point, recorded at the Hive's scope and written by `hive-imperative render` into every Imperative of the class. A playbook is these rule records and nothing else, and the dispatch matrix, which maps a class to its profiles and placement, holds none of it.
- Expired and lifted rules, archived words and abandoned trials stay readable and are not loaded as current policy. A missing rendered field is not proof that a rule was retired.

A project's ruling on its systems, which the design's [A project's systems, asked at intake](../docs/design.md#a-projects-systems-asked-at-intake) asks for when the project is registered, is a rule record at the project's scope like any other: its words are the Hive Mind's answer, kept exactly, and a later answer that changes the list amends or supersedes it.

The Shadow reads rules with an expiry through `hive-pool read` with `due_before`, and the UI's Scheduled view reads them the same way, with their receipts.

## Generated knowledge

`hive-memory` derives instructions from the effective rules and each fact's canonical owner, and records what each consumer received. Schema: [`records/pool.projection.v1`](schemas/records/pool.projection.v1.schema.json). One projection exists per scope and audience (`shared`, `fleet`, `project`); a re-render is a new rendering of the same record.

- **`render`** resolves the rules for the scope at the given instant, renders the text, records the sources at the revisions read, the renderer version, the resolved-rule digest and the text's digest, and writes `pool.projection.rendered`. A rendering equal to the current one by digest writes nothing. At stage 2 the sources are rules; a later stage that owns another kind of fact adds it as a source kind by a minor change.
- **`check`** reports, against the budgets given, each projection's state, size and budget standing, its stale sources, rule lines duplicated between projections of one scope, and consumers whose received or acknowledged digest is not the current one. It repairs nothing. **Freshness is computed, never stored**, here and at `hive-pool read` of a projection, from the rules in force at that moment: the check resolves the rules for the projection's scope as `render` did, at the clock, and the projection is `fresh` only when they resolve to the rendering's `rules_digest` with no conflict. A rule added after the rendering, a temporary rule that has expired by the clock or become effective by it, a lift, an end and a changed revision each make it `stale` with no receipt and no writer having touched it; its stale sources are the rules whose revision differs, the rules now in force that it did not read, and the rules it read that are no longer in force.
- **`propagate`** records one consumer's receipt, or acknowledgment, of a rendering at a digest, each with its own receipt: `pool.projection.received`, `pool.projection.acknowledged`. A step already recorded is returned unchanged.
- A projection is `stale` whenever the rules in force no longer resolve to the rules digest it was rendered from, `rules_digest`, which is the resolved-rule digest and never the digest of the rendered text: the freshness comparison in `check` and in `hive-pool read` names the rules digest, so an unchanged rendering of changed rules is stale and a changed rendering of unchanged rules is not. No writer marks it, so a rule written, expired or lifted cannot leave one fresh. A stale projection cannot authorize work; the consumer that refuses one is stage 4's, and reads freshness through `hive-pool read` or `check`.

The maintenance queue the design names, into which a stow enqueues uncovered knowledge, is left to the stage that builds stow.

## Legacy import and export

The legacy Markdown backlog is an import and export format, not a second queue. Its grammar is the upstream's, translated; see [import-plan-tasks-axi.md](import-plan-tasks-axi.md). Schema of the migration: [`records/pool.migration.v1`](schemas/records/pool.migration.v1.schema.json).

**`import-legacy`** reads one file at the physical path the request names, in the zone it names, and parses it with the translated grammar. With `dry_run` true it returns the report and writes nothing. With `dry_run` false it requires that the parsed file renders back byte for byte (`round_trip_exact`), refuses otherwise with `pool.legacy_not_round_trip`, and in one transaction writes one `pool.migration` holding the source text and every entry's exact lines, one item per entry with an identifier, a hold for each entry with hold tags, and the receipts `pool.legacy.imported` and, per record, `pool.item.added` and `pool.hold.placed`. `expected_digest` makes the caller import what it inspected. The file is never written, and a second import of the same source digest into the same home is `already_exists`. An imported item takes no level and no parent from its title; the owner sets them after the import, a level by `update` as [Levels](#levels) defines it, which makes an imported queued item with no generation a Target when its owner says so.

| Legacy form | Pool |
| --- | --- |
| `## Queued`, `## In flight`, `## Done` sections, a header suffix allowed | `state` `queued`, `in-flight`, `done`; other sections pass through as free lines |
| The bullet's identifier | `legacy.legacy_id`; the item gets a minted `task_id` |
| The prose before the tags | `title`; indented continuation lines are `body` |
| `(repo: x)`, `(kind: x)`, a leading kind word such as SHIP or SCOUT | `legacy.repo`, `legacy.kind`, verbatim; nothing is inferred into `deliverable` or `class` |
| `(priority: n)` | `priority` |
| `(since DATE)`, `(merged\|reported\|done\|closed DATE)` | `created_at`, and for a Done entry `completed` with `closed_at`, at the start of that day in the import's zone. A Done entry with no closing date is imported completed with its time unknown: `completed` is set, `closed_at` is left absent and `closed_at_unknown` is set, and no time is invented for it, the time of the import least of all, which the migration record carries as its own fact |
| `(hold: reason)`, `(hold-kind: captain\|external\|load\|parked\|future)`, `(hold-until: DATE)` | A hold of kind `word`, `external`, `resource`, `parked` or `future`, with `until` kept as instant, zone and the date as written; on a `word` hold the date is a revisit date and never makes the hold inactive |
| `blocked-by\|parent\|discovered-from: <id> - <reason>` | `deps`, resolved to the `task_id` the same import minted; an edge to an identifier the file does not hold is kept in `legacy.meta` and treated as resolved |
| Pull request URLs, `data/<id>/report.md` paths, other URLs in the prose | `links` of kind `harvest`, `report`, `doc` |
| A `PERSISTENT SECONDMATE` entry, or any entry the design's rule names as a persistent supervisor | **Excluded**: no item is created, the entry is recorded in the migration with its reason and its lines, and the export emits it verbatim. A persistent Fleet never becomes an ordinary task. |
| A public-followup marker and its body | Kept in `body` and `legacy.meta` verbatim; the upstream's public-followup state machine is not translated |
| Free-form lines without an identifier, the preamble, carriage returns, the final newline | Kept in the migration exactly, never addressed by identity |

**`export-legacy`** renders items in the legacy format and returns the text, its digest and size; it writes no file. With a `migration_id`, it emits the source's preamble, sections, free lines and entries in the source's order: an item unmodified since its import is emitted from its exact original lines, where unmodified means that the item is at the `record_revision` the import wrote and the holds on it are exactly the holds the import placed, each at the revision the import wrote: a hold placed or released since the import makes the item modified, because the legacy form carries the hold in the entry's own tags; a modified item is re-rendered canonically; every item is emitted in the section its current state maps to, a queued or in-flight item that has landed, a landed Target and a landed Prey with Hunts included, being read as done, because they store no completion of their own and a re-import, which carries no level, reads them as the completed leaves they then are, so that the `blocked-by` edges that name them stay satisfied; the legacy form tells a queued entry from an in-flight one by the section alone: an item whose state still maps to its source section keeps its source place, an item whose state has changed, by a transition, a completion or a reopening, moves to the end of the first section of the file that maps to its present state, or under a canonical header appended after the last section where the file has none; an excluded entry is emitted verbatim. An archived item is not suppressed: archival has no form in the legacy format, so it is exported in the section its state gives, one that has landed among the done entries and one archived without having been done in the section it was archived from, so that a blocker that never completed still blocks after a round trip. `exact` is true when the text equals the source. Without a migration, or with `normalize`, every item the selector matches is rendered canonically, as the upstream's `render` verb does. Legacy words are rendered from the `legacy` member and Hive-only fields are not written into the legacy form. A canonical rendering writes hold tags for the item's active holds only, so a released hold is never written back.

`test-pool` proves the round trip on the two upstream fixtures re-expressed as Hive fixtures, on a file with every tag the table names, and on a file with carriage returns, a header suffix and an unrecognized section; it proves a persistent-supervisor entry excluded; and it proves that an import into a home inside a repository is refused and that an import never writes the source path.

## Reading the Pool

`hive-pool read` is the one way another package sees the Pool. It reads one kind by identity or by query, takes no lock for a read of one record that stands alone, and the lock shared for every other read: a list, and an item or a projection selected by identity, whose derived facts read several records and which therefore must see an interrupted transaction recovered first, and returns every record whole with a **projection header**: the home, the time of the read, the journal cursor at that moment and whether the read was complete. A record that cannot be read is omitted and named, never guessed; an incomplete read says so and is never an authoritative empty result.

| Reader | Reads | How |
| --- | --- | --- |
| `dispatch`, stage 4 | The item it dispatches, its admission in state `admitted` and the accepted specification revision; the Imperative by `render` | `read` with kinds `item`, `admission`, `specification`; `hive-imperative render` |
| `spawning-pool`, stage 3 | Nothing by call: the dispatcher passes `task_id`, `generation` and the requested place in each request | |
| `shadow` | Active holds with an `until`, rules with an expiry time, each due at or before an instant | `read` with `due_before` |
| `ui` | Items with their derived facts, holds, rules in force and recently expired, projections | `read` by query |

## Receipts and events

The twenty-five receipt kinds are registered in [`packages/pool/hive-package.json`](../packages/pool/hive-package.json), each with the one fact it asserts. Every one has an empty body: the fact is carried by the receipt's `subject`, the record at the revision the fact holds for, and its `evidence`. Each is written inside the transaction that establishes its fact, at most once per request, kind and subject.

The Pool registers these event kinds, each with an empty body and a `basis` naming the receipt that establishes it:

`pool.item.added`, `pool.item.transitioned`, `pool.hold.placed`, `pool.hold.released`, `pool.generation.opened`, `pool.generation.closed`, `pool.admission.checked`, `pool.imperative.revised`, `pool.specification.accepted`, `pool.specification.invalidated`, `pool.specification.closed`, `pool.rule.recorded`, `pool.rule.amended`, `pool.rule.expired`, `pool.rule.lifted`, `pool.projection.rendered`, `pool.legacy.imported`.

`pool.admission.checked` is one event for the three check receipts. An event is appended in the transaction of its receipt, after the records and receipts, and its scope and `task_id` are the subject's.

## Decisions taken here

Where the design was silent, this file reads it as follows. Each decision is followed by the alternative it rejected.

1. The design's five-step passage is `state` and `definition` read together, so the legacy three states keep their transitions unchanged; the alternative, one five-valued state, would make the legacy import map a queued item to a guessed definition state.
2. Holds are records of their own, not fields of the item; holds as fields could not be named by `error.hold` or a wake and would vanish with the item's archive.
3. A generation is an entry of the item, not a record of its own: it has no identity but the item's and its number; a `pool.generation` record with a composite identifier would be one more file per launch with no second reader.
4. The Imperative is keyed by its item, one record with all revisions; an `imp_` identity would be one more prefix with no second reader.
5. The admission check is repeatable and every check is kept; `approve` records a ruling and the caller checks again; one check per admission would need a new admission for every re-check at a launch path.
6. The place and the branch's state are evidence the caller supplies; the Pool runs no Git; the Pool reading the clone would give it a core dependency and a worktree assumption.
7. The decision intake and the records it persists are not defined here: they wait for the operator's ruling on what proves an answer, and are defined in a definition of their own in this stage; see Left undecided. The Pool defines only the hold kind `word` that the intake places and releases.
8. Moving items between homes is deferred to the stage that builds routing, which defines it on the upstream's multi-item move as its base; see Left undecided. The `handoff` field of an item stays as the stage-4 route's way to hand one item to a child Fleet.
9. The rule line is supplied by the recorder; the resolver appends the source. Conflicts are reported, never resolved by the store; a line derived from the words would be an interpretation the store makes on its own.
10. A legacy kind word is kept verbatim and never mapped to a deliverable or class; a mapping table would invent intake decisions.
11. One `read` operation on `hive-pool` serves every Pool record kind, with a projection header; a read operation per command would be ten more schema pairs of the same shape.
12. Every receipt has an empty body, the subject at its revision and the evidence carrying the fact; body schemas would be twenty-five more files repeating the records.
13. The six new prefixes are declared in this file and in the `$defs` of `records/pool.item.v1`, and registered in `identities.md` and `contract/ids` by the first change of the build in one commit, because `test-contract` holds the table and the registry in step and the definition may not edit `contract/`; adding the rows in the definition would have failed `test-contract`.
14. A `check` that refuses or holds returns no body, with its findings in the record and the receipts, so that no non-`ok` response carries a partial result; a body on refusal would be the partial result the command contract forbids.
15. The plan's order inside the stage, read-only import first, round trip and crash recovery proved, then one writer selected, is read as an order of proofs, not a calendar: the grammar and the read-only import start at once and touch no store, the legacy writer waits on the round trip and on the store, the one writer is the store under one lock with roll-forward, proved before the stage is accepted, and the contracts of stages 3 and 4 land first because nothing in them writes from a legacy file; a strictly serial stage would delay those contracts by the length of the translation and gain nothing, since the grammar and the store share no code.
16. `codex-cloud` is refused unconditionally at stage 2, in the check itself, and admitted only after the later minor change [the execution place](#the-execution-place) names, once Codex Cloud is back in scope; a parked flag in a rule or configuration record could be flipped by a value, which the design's rule that a parked backend is refused and never substituted rules out.
