# Version 2.0

Version 2.0 begins the ordered Pool memory definition with subjects, canonical facts and provenance, per-projection budgets, and kind-tagged operating and product rules.
[pool.md](../pool.md) owns these records and their semantics, including the conflict key versus filing subject, the 300-character line cap, atomic subject/fact creation and the word-only budget change.
The subject and budget records and budget operation bodies start at 1.0; the rule record and incompatible rule operation bodies use their v2 schemas.
The unchanged amend, expire and resolve request bodies remain current at v1, with resolve reading the unchanged role definition from the current rule schema.
The specification record at 1.1 and define body at operation version 1.1 add the product-rule bindings and governed stage that the rule contract uses, while keeping their existing fixture deferrals.
The Pool declaration, read alternatives and complete new-schema fixtures change with their contracts.

This is the first incompatible group of the definition and takes the major version under [Changing a contract](../README.md#changing-a-contract).
Superseded v1 rule schemas and their deferral rows are removed: they have no built or importing producer and no record of them can exist.
No runtime migration is invented for nonexistent records.
The three still-current rule request schemas keep their fixture deferrals.
No package owner or dependency changes.

[Layout rule 9](../layout.md#rules) specifies the terminal major suffix for fixture directories; this group includes its walker implementation and acceptance tests in contract/schema/fixture_obligations_test.go and fixtures_test.go.
The tests exercise separate major proofs, missing successor proof, deferrals, malformed directory names and common definitions rather than checking source strings.
The full fixture walk is required by this group's validation.
The later projection, maintenance and additive specification groups complete the definition before their dependent producers are built.
The executable contract-version constant stays at its last built version until a producer implements these demands.
