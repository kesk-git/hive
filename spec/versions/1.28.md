# Version 1.28

Version 1.28 keeps the diagnostic detail of a failed command in one place, the home's event journal, and takes it out of the response and standard error.

A response's `error.message` is one sentence naming the field and shape that failed. It carries no lower-layer error chain, no typed text and no panic value; a message names a position or a kind and a byte length at most, and never quotes an argument, an option, a command name or an operation name. Standard error for a response that is not `ok` is exactly one line, `<command> <operation>: <status> <code> <request_id>`, with `-` for an absent operation or request_id and no message text; a failure that gives no response at all keeps its own line, and a panic's stack no longer goes to standard error.

What a failure held beyond its message goes, where a home is named and its executable configures a journal that opens, into the home's event journal as one diagnostic event of the answering package, [`<package>.diagnostic.recorded`](../events.md#diagnostic-events), written through the contract library's journal like every event and correlated by `request_id` and `correlation_id`. It is the one kind common to every package: each package owns its own instance, and all share the one body schema [`events/diagnostic.recorded.v1`](../schemas/events/diagnostic.recorded.v1.schema.json), which the journal resolves for any of the seven package names. Its basis is the observation of the request that failed, or, for a request that could not be read, of the invocation. It is written only for a failure that has a lower-layer error chain or a panic, never for an `ok` or a replayed response, and a failed append changes nothing in the response. The single exception to "nothing was changed" for a non-`ok` status and to "read-only operations record nothing" is this one event.

It is a minor change by the rule of [spec/README.md](../README.md#changing-a-contract): it registers one event kind and adds no operation, no record kind, no package and no dependency; every record, receipt and event valid under 1.27 is valid under 1.28; and the library's contract version constant does not move. The Scheduled view of the design states that every entry shows its freshness as one state word, with its source revision in its source-health entry.
