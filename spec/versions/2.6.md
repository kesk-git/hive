# Version 2.6

Version 2.6 brings the request schema of `hive-rule record` into line with the refusal the [Rules](../pool.md#rules) section already states: `record` refuses a rule line over 300 characters with `pool.rule_line_too_long`, naming the measured count, the cap and the recorder's three moves.
The request's `rule_line` keeps `minLength: 1` and no longer carries `maxLength: 300`, which made that refusal unreachable: the harness answered `schema_violation` before the operation ran.
The record schema `records/pool.rule.v2` keeps its own cap of 300, so no rule line over the cap is ever stored.

It also corrects the record schema `records/pool.rule.v2` for a rule whose expiry an `end` amendment set: `expire` notices the effective expiry, the latest amendment's `new_expires_at` where there is one, so a rule recorded without `expires_at` and ended on a date is expired like any other. The `then` branch for status `expired` now requires `expiry` only and no longer `expires_at`; the original dates are never written, and a rule that carries `expires_at` is as valid as before.

It also states in [Rules](../pool.md#rules) what `hive-rule record` and `amend` already refuse: an `extend` or `end` moving the expiry the wrong way, an `extend`, `end` or `lift` of a rule no longer in force, a `changes` naming a rule of another conflict key or full scope, and a second product rule in force on one conflict key and full scope; each is a refusal of an operation that did not exist before, so no record or request valid before is invalid after.

This is a minor change under [Changing a contract](../README.md#changing-a-contract): every request valid before the change is valid after it, a line over the cap, once invalid by schema, is now refused by the operation with its own code, and every stored rule valid before is valid after.
